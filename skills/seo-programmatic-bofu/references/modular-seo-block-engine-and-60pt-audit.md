# Модульный блочный движок SEO-сайта и протокол экспресс-аудита

> [!NOTE]
> Инженерный синтез Q1 2026. В названии файла «60pt» — это итоговый балл учебного протокола (60 из 100, оценка C),
> а не число пунктов: сам протокол содержит 75 взвешенных проверок в 11 группах. Здесь он пересобран в формулу
> скоринга и гейты. Используется навыком `seo-programmatic-bofu`: программные BOFU-страницы рендерятся этим движком.

## 1. Зачем блочный движок программному SEO

Хардкод страниц (текст внутри разметки) ломает три вещи, нужные массовым посадочным: нельзя сменить нишу или цену
без правки вёрстки; нельзя автоматически проверить уникальность страниц; SEO-поля добавляются в конце и теряются.
Движок разделяет **данные** (что сказано), **блоки** (как показано) и **маршруты** (где лежит).

```
data/site.json          ── бренд, контакты (NAP), соцпрофили, дефолтные OG
data/pages/<slug>.json  ── страница = { slug, type, seo{}, blocks[] }
blocks/registry         ── тип блока → компонент + схема props + вклад в JSON-LD
renderer                ── проходит blocks[], валидирует props, рендерит по порядку
routes                  ── /services (хаб) → /services/[slug]; 404 для неизвестного slug
build                   ── sitemap.xml из slug без draft; robots.txt; head-SEO из seo{}
```

### 1.1. Контракт страницы

| Поле | Тип | Правило |
|---|---|---|
| `slug` | kebab-case, латиница | ЧПУ вида `/services/detailing`, без параметров |
| `type` | enum: hub, service, service_geo, comparison, alternative, article | определяет обязательные блоки |
| `seo.title` | строка 30–60 симв. | уникальна по сайту |
| `seo.description` | строка 70–160 симв. | уникальна по сайту |
| `seo.canonical` | абсолютный URL | по умолчанию — сам себя |
| `seo.og` | image, title, description | картинка 1200×630 |
| `draft` | bool | `true` → нет в sitemap, `noindex` |
| `blocks[]` | список `{type, props}` | порядок в данных = порядок на странице |

### 1.2. Реестр блоков (минимальный набор)

| Блок | Обязательные props | Владеет | Вклад в разметку |
|---|---|---|---|
| Hero | h1, lead, cta | единственным H1 страницы | — |
| Services / Offer | items[{name, price, unit, url}] | H2 | `Service` / `Offer` |
| Facts / Specs | rows[{name, value, source}] | таблица | — |
| Steps / Process | steps[] | нумерованный список | `HowTo` (если уместно) |
| Comparison | columns[], rows[] | таблица сравнения | — |
| FAQ | qa[{q, a}] | H2 + список | `FAQPage` (только видимые пары) |
| Reviews | items[] с источником | — | только реальные отзывы, без вымышленных рейтингов |
| Breadcrumbs | path[] | навигация | `BreadcrumbList` |
| CTA / Contacts | phone (`tel:`), messenger, form | конверсия | `Organization.contactPoint` |

Правила движка:

1. В компонентах нет текста: всё приходит через props из данных.
2. H1 рождается только в Hero; второй Hero на странице — ошибка сборки.
3. Блок без обязательных props не рендерится и валит сборку (а не выводит пустую секцию: пустые секции — пункт аудита).
4. JSON-LD собирается из вкладов блоков в **один** `@graph` со стабильными `@id` (см. §5).
5. Смена порядка блоков в данных меняет страницу без правки кода — это и есть «перекраска ниши одним промптом».

### 1.3. Рендеринг для ботов

Клиентский SPA отдаёт боту пустой контейнер. Для SEO-страниц движок обязан отдавать HTML с контентом: SSG для
блогов и посадочных (быстрее всего), SSR для порталов с частыми обновлениями и кабинетами, headless CMS — когда
контент правит команда без доступа к коду. Проверка: исходный код страницы (не DevTools) содержит H1, текст блоков
и JSON-LD; при выключенном JS контент виден.

## 2. Пайплайн разработки: 10 этапов с условиями входа

| # | Этап | Вход (нельзя начинать без) | Выход |
|---|---|---|---|
| 1 | Архитектура страниц | семантика/кластеры | дерево URL, типы страниц, 404 и «спасибо» |
| 2 | Дизайн-правила | этап 1 | шрифты, 2 цвета, отступы, кнопки (UI-кит) |
| 3 | Каркас | этап 2 | репозиторий, фреймворк, CSS-утилиты, типизация, линтер — до компонентов |
| 4 | Контент и маршруты | этап 3 | реальные тексты/цены/картинки в данных, затем маршруты (content first) |
| 5 | Блоки и шаблоны | этап 4 | реестр блоков, шаблоны страниц по типам |
| 6 | Тех-SEO в компонентах | этап 5 | head из данных, семантические теги, JSON-LD из блоков |
| 7 | Скорость | этап 6 | WebP/AVIF, lazy, шрифты с `font-display: swap`, критический CSS |
| 8 | Аналитика | этап 1 + этап 6 | счётчики и цели (телефон, мессенджер, форма) |
| 9 | Деплой | этапы 1–8 | DNS, TLS, обновление одной командой |
| 10 | Поддержка | этап 9 | правка цены/телефона в данных за минуты |

Нарушение порядка создаёт долг: типизация после компонентов, вёрстка до реального контента (заголовок в две строки
ломает карточку), аналитика до архитектуры страниц.

## 3. Definition of Done (приёмка каждой задачи для ИИ-агента)

| # | Критерий | Как проверяется автоматически |
|---|---|---|
| D1 | Консоль браузера без ошибок | headless-браузер, 0 errors |
| D2 | Mobile-first от 320 px, без горизонтального скролла | скриншоты 320/768/1280, ширина документа ≤ окна |
| D3 | Уникальные title/description, иерархия H1→H2→H3, alt у изображений | краул собранного сайта |
| D4 | ЧПУ без `?id=` | regex по sitemap |
| D5 | Lighthouse/PSI Performance ≥ 90 на шаблонах | PSI API по одному URL каждого типа |
| D6 | Формы отправляют данные; `tel:` и мессенджер кликабельны | e2e-сценарий |
| D7 | Своя 404 с ссылкой на главную, ответ 404 | запрос несуществующего URL |
| D8 | sitemap.xml и robots.txt генерируются; draft исключены | сравнение sitemap со списком slug |
| D9 | OG-картинка и favicon | разбор head |
| D10 | Форматирование, структура папок, коммит | линтер + git status чистый |

DoD прикладывается к каждому поручению агенту: без него агент «разносит» проект правками вне задачи.

## 4. ИИ как технический директор: контракт проекта

1. **Выбор стека через сравнение**: агенту дают задачу сайта и просят таблицу SSG / headless CMS / SSR по SEO,
   скорости и стоимости поддержки. Решение фиксируется в документации.
2. **Файл правил проекта** (подгружается в каждый запрос): стек; размещение (`app` — только маршруты,
   `components/ui` — «глупые» компоненты, `components/blocks` — блоки, `lib` — утилиты); запрет компонентов в корне;
   нейминг (PascalCase для компонентов, camelCase для утилит, kebab-case для URL); язык ответов; «полный код без
   заглушек»; ключи доступа только в переменных окружения, не в репозитории; обязательная сборка после правки.
3. **Скаффолдинг** по правилам: пустые папки с индексными файлами, линтер, команда запуска.
4. **README + ONBOARDING** генерируются сразу и обновляются после каждого патча.
5. **Тест пустого чата**: новая сессия без истории должна правильно ответить, куда и как добавить новый блок.
   Не прошла — документация неполна.
6. **Режим по размеру правки**: точечная правка — inline; понять/спланировать/провести аудит — чат; многофайловое
   изменение — composer/агент. Каждый diff просматривается до принятия; head и консоль проверяются руками.
7. **Модель по сложности**: лёгкие модели и автоподбор — для простого, модели класса Sonnet — основная работа,
   тяжёлые — редко (быстро съедают лимит); свой API-ключ не отменяет подписку IDE и добавляет наценку.

## 5. Микроразметка как граф (вклад блоков)

- Три слоя: сайт (`Organization` + `WebSite` на всех страницах), страница (`WebPage` и подтипы `CollectionPage`,
  `AboutPage`, `ProfilePage`, `FAQPage` + `BreadcrumbList`), контент (`Article`, `Service`, `Product`, `VideoObject`).
- Стабильные `@id`: `SITE/#org`, `SITE/#website`, `SITE/#person/{slug}`, `SITE/{path}/#webpage`,
  `SITE/topic/{slug}/#collection`, `SITE/#term/{slug}`. Сменить `@id` = выдать сущности новый паспорт.
- Связи: `isPartOf`/`hasPart` (страница ↔ хаб), `author`/`publisher`, `about` (главная тема) и `mentions`
  (второстепенные), `sameAs` — только официальные профили.
- Размечать только видимое: никаких вымышленных `Review`/`AggregateRating`; один `@graph` вместо разрозненных блоков.
- Двухфазный процесс внедрения: (1) карта типов страниц → типы схем → `@id` и связи → утверждение; (2) JSON-LD
  по одному типу страницы с указанием, откуда берётся каждое поле; валидация в Rich Results Test и валидаторе схем.

## 6. Протокол экспресс-аудита: 75 проверок → 7 измерений → балл

### 6.1. Формула

```
status_i ∈ {OK = 1.0, WARN = 0.5, ERR = 0.0, N/A — исключить из знаменателя}
балл_измерения_d = max_d × Σ(w_i × status_i) / Σ(w_i)       по проверкам измерения d
итог = Σ балл_измерения_d                                    (0..100)
```

Коэффициент WARN = 0,5 — реконструкция для воспроизводимости; в исходном протоколе веса заданы, а частичный зачёт
явно не описан.

| Измерение | max_d | Группы проверок |
|---|---|---|
| Техническое здоровье | 17 | техника, инфраструктура |
| Качество контента | 20 | контент, QRG-LITE |
| Разметка и структура | 15 | структура, локальные ловушки |
| Производительность (CWV) | 12 | CWV |
| Видимость в выдаче | 16 | видимость, индексация |
| Потенциал роста | 8 | история домена |
| AI-видимость | 12 | доступ ботов и клоакинг |

Статус измерения: ≥ 85 % — норма; 40–84 % — внимание; < 40 % — критично. Итог 60/100 соответствует оценке C.
Предлагаемые полосы оценок для графа: A ≥ 85, B 70–84, C 55–69, D 40–54, E < 40.

### 6.2. Проверки и пороги (вес в скобках)

**Техника**: валидный TLS (8); TTFB ≤ 0,5 с (6); HTTP/2 (3); сжатие gzip/br (4); robots.txt есть и не закрывает
нужное (9); sitemap найден и > 10 URL (7); главная отвечает 200 (10); редиректов ≤ 2 (5); meta viewport (8);
нет запрещающего X-Robots-Tag (10); нет запрещающего meta robots (10).

**Контент**: title 30–60 симв. (9); description 70–160 симв. (5); ровно один H1 (7); ≥ 500 слов на ключевых
страницах (6); alt у ≥ 80 % изображений (2); Open Graph (3); lazy-load и WebP/AVIF (4); нет заглушечного текста (10);
пустых секций (заголовок без текста) < 10 (5).

**Структура**: ≥ 2 H2 (5); хотя бы один тип Schema.org (6; JS-вставленная разметка парсеру не видна — перепроверить
валидатором); canonical задан (8); согласованность H1 по выборке страниц 0,8–1,2 (4); доля текста в HTML ≥ 15 % (3).

**CWV**: PSI Performance ≥ 50 (7); LCP ≤ 2 500 мс (8); CLS ≤ 0,1 (7); INP ≤ 200 мс (6; без полевых данных — N/A).

**Видимость**: > 10 запросов в топ-10 (8); > 50 в топ-50 (5); бренд в топ-3 по брендовому запросу (9); > 5 запросов
с частотой > 100 (7); видимость в сервисе ключей > 100 (6); коммерциализация и геозависимость — справочно (5).

**Индексация**: страниц в индексе ≥ 50 % sitemap (8); главная в кэше (5); индекс не превышает sitemap (иначе мусор
или дубли) (7).

**История домена**: возраст ≥ 2 лет (4); > 100 ключевых слов (5); средняя конкурентность ниши ≤ 10 из 25 (6);
чистота в DBL (9); нет токсичной истории в архиве (8); домен не дроп (7).

**Доступ ботов**: нет клоакинга (10); AI-боты не заблокированы (5); Googlebot получает 200 и разрешён (10);
YandexBot — то же (8); безопасный сайт по обоим поисковикам (9).

**Инфраструктура**: CMS определена (3); HSTS (4); нет дубля www (7); DOM ≤ 1 500 узлов (5); доля клиентского
рендера < 30 % (8); ≥ 20 внутренних ссылок с главной (6); ≤ 10 сторонних доменов (4); ≤ 10 внешних скриптов (5).

**Локальные ловушки**: нет гео-конфликта title и description (8); гео не только в description (5); автор в
разметке не обезличенный (4); один адрес NAP (6); NAP в разметке = NAP в подвале (7); нет Article-разметки на
главной (3).

**QRG-LITE** (детерминированная оценка, максимум 43): сигналы доверия ≥ 4 из 7 (7); страница о компании ≥ 3 из 5
(6); контакты ≥ 1 из 3 (5); юридическая прозрачность ≥ 1 из 3 (4); классификация YMYL (3); реклама не мешает (4);
автор идентифицирован ≥ 2 из 4 (5); знаки доверия ≥ 1 из 3 (4); title и H1 соответствуют интенту ≥ 3 из 5 (6);
«вода» ≥ 3 из 5 (5); навигация ≥ 1 из 2 (3); итог QRG-LITE ≥ 60 % (7).

### 6.3. От протокола к экспресс AI-аудиту

1. Автоматический прогон (без LLM): все 75 проверок, карточка сайта, балл.
2. Топ-10 проблем с приоритетом N/10; для каждой — «обнаружено / норма / позиция Google / позиция Яндекса / решение
   и модуль работ». Позиции поисковиков — только со ссылкой на источник, иначе пометка «гипотеза».
3. Ручная верификация моделью и человеком: каждая проблема подтверждается URL-примером.
4. План модулей: технический аудит → мониторинг индексации → бриф и структура кластера → аудит страницы и
   разметка → поведенческий скоринг (нужен доступ к аналитике).
5. Резюме для владельца бизнеса без жаргона.

Типичные критичные находки учебного примера и их классы: весь контент на одном URL (нет страниц под интенты);
robots.txt закрывает страницы, которые должны ранжироваться, и страницы доверия; аккордеоны без видимого текста;
LCP 7–8 с из-за дублирующихся скриптов и шрифтов; отсутствие `lang` и разметки.

## 7. Связка с `seo-programmatic-bofu`

| Шаг BOFU | Что даёт движок | Проверка |
|---|---|---|
| Матрица кандидатов | строка матрицы → `data/pages/<slug>.json` | slug уникален, тип из enum |
| IG-2 уникальные факты | факты живут в блоке Facts/Specs с `source` | ≥ 3 факта на страницу, не повторяются в батче |
| COS антиканнибализация | вектор считается по тексту блоков без Hero/CTA/Contacts | порог как в навыке |
| Дорвей-риск | доля общего текста блоков между страницами батча | см. гейт BE-3 |
| Пачка в Контент завод | CF возвращает props блоков, а не HTML | схема props валидна |
| Релиз волны | draft → false только для прошедших гейты | sitemap = опубликованные slug |

Метрика дорвей-риска для пары страниц батча: доля совпадающих шинглов текста блоков (без Hero, CTA, Contacts,
Breadcrumbs). Если страницы различаются только подстановкой города или названия в одинаковые блоки — это дорвей,
даже при прохождении косинусного гейта.

## 8. Детерминированные гейты

| Гейт | Правило | Провал → |
|---|---|---|
| BE-1 нет хардкода | компоненты блоков не содержат текстовых литералов (кроме служебных подписей интерфейса) | вернуть в этап 5 |
| BE-2 один H1 | на странице ровно один Hero | `build_error` |
| BE-3 дорвей | общий текст блоков пары страниц батча < 0,6 по шинглам | `blocked_doorway` |
| BE-4 видимая разметка | каждый узел JSON-LD соответствует видимому блоку; нет вымышленных рейтингов | убрать узел |
| BE-5 бот видит контент | H1, текст блоков и JSON-LD есть в исходном HTML | включить SSG/SSR |
| BE-6 sitemap | sitemap = slug с `draft = false`; ни одного `?id=` | пересобрать |
| DOD | все 10 пунктов §3 зелёные на одном URL каждого типа | задача не принята |
| AUD-1 балл | итог протокола ≥ 70 перед масштабированием шаблона | сначала исправить ERR с весом ≥ 8 |
| AUD-2 критичные | ни одной ERR из: главная не 200, запрещающий robots/X-Robots-Tag, клоакинг, Googlebot закрыт | `blocked_release` |
