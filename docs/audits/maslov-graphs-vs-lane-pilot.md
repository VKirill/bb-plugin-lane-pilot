# Видение Матвея (систематизировано)

Источник: сообщения 28964–31947 в «Изнанке» + репо agent-work-graphs (README = его же слова, публичная версия).

**Ядро: «машинист — модель, рельсы — код».**

1. **Всё детерминировано, решает код, не модель.** Демон двигает работу по нодам, включает оркестратора (тоже модель) на поворотах, оркестратор включает работников. Модель не может поехать туда, где нет рельс (#31764–31786).
2. **Граф = путь с доказательством на каждом шаге.** «Done» ставит независимая проверка по контракту, не тот кто делал. Слову агента код не верит: сданный код прогоняется в чистой копии (#31865).
3. **DoD многоуровневый**: задача → фаза → проект → волна. Пункт задачи закрывает пункт фазы, пункты фазы — пункт проекта (#31857–31859).
4. **Тесты — часть задачи с самого начала, до старта агента.** Код сам гоняет проверку до агента и видит красное; после — зелёное в чистой копии; потом отдельный критик смотрит «решена ли задача по сути, а не подогнана под тест» (#31865).
5. **Возвраты нелинейны, но по рельсам.** «Можем из 4 вернуться в 1, из 5 — в 2». Самоулучшение: поезд на голове А, проблема в 6 → меняет голову, гонит со 2-й ноды, пропускает 4-5, продолжает (#31587–31589). Оунер может в любой момент докинуть контекст/остановить/изменить (#31575).
6. **Loop guard**: 3 ходки не помогли → меняется перспектива (big picture, охотники ищут дольше) → ничего не помогло → беклог, разбор по полной (#31601–31602).
7. **Итерации ограничены.** «Проверяющий бесконечно находит дыры» → лимит итераций, скейл приёмки результата, 1–3 рекомендации за цикл, каждая с доказательством, метрика на фиксированном наборе 20–50 задач, не стало лучше → откат (#30955–30962, #31448).
8. **Изменение самого графа/модели — только через «да» оунера** при отсутствии откатов (#31448).
9. **Графы маленькие и множественные.** «Система стройки маленьких графов… любой новый процесс попадает в кодекс как маленький граф» (#31916). Набор графов, модель использует когда нужно (#31469).
10. **Каждая стадия логируется и улучшается.** Проверка стадии — кодом (сделано/не сделано), не мнением модели. Ночной дебаггер чинит класс ошибок, не случай. Лог-лист, токены и время на стадию (#31448).
11. **Проверяющий бесконечен → границы.** Отдельные роли: code (Sonnet), code checker (Opus), plan (Opus), verifier (astra), debugger (Opus) (#31697).

**20 вопросов-аудит из agent-work-graphs** — эталон: контракт до старта; done ставит не исполнитель; человек видит контракт+доказательства+риски; каждое доказательство перезапускается одной командой; изоляция (своя копия/ветка/юзер); откат одним действием; агент не может прочитать ключ приёмки; статус производный от event log; «вопрос агента» ≠ «сдача работы»; неизмеренные затраты показаны как «не измерено»; пауза/стоп/коррекция на всех уровнях переживает рестарт; провал → чек против повторения; весь путь пройден живьём несколько раз.

# Пробелы (приоритет по боли из его рассказов)

## P0 — «Слову агента код не верит» не доведено до конца

- **Нет стадии критика «решена ли задача по сути» после writer.** Матвей: отдельный агент-критик смотрит не подогнано ли решение под тест, и заметно ли что агент лез в сами тесты. У нас: `qa-gate` = прогон проверок; code critique существует, но покрытие ~2% и это не обязательная нода в lp-task-pipeline. Добавить ноду `substance-critique` после `qa-gate` (или в `browser-qa` слой) + детект «агент трогал тесты» (path ownership diff уже есть — завести в проверку).
- **DoD одноуровневый.** У Матвея пункт задачи закрывает пункт фазы → фазы закрывают проект → волны со своим DoD. У нас DoD живёт в задаче, run-level цели аудируются `closeAfterAudit`, но **фазы/проекта с накапливающимся DoD-контрактом и cross-level rollup нет**. Реально: `phase` комната есть, но нет связи «пункт фазы ← пункты задач».
- **Verification command не записана в контракт задачи до старта.** Матвей: команда проверки фиксируется в задаче, код прогоняет её ДО агента (должна быть красной) и ПОСЛЕ (в чистой копии, зелёной). У нас baseline red check есть частично, но контракт «какой командой проверяем» не обязателен в задаче — при отсутствии верификация деградирует в мнение модели.

## P1 — Loop guard внутри хода (уже найдено ранее, повторяю в этом списке)

- `writer-silence` ловит только молчание. Активный цикл «та же ошибка N раз» живёт без надзирателя — у Матвея это «3 ходки → смена перспективы → охотники → беклог» на уровне темы, у нас оно есть только **между** попытками (topic-loop), не **внутри** живого хода. План: `writer-loopwatch` рядом с writer-silence.

## P1 — Самоулучшение без фиксированного набора и границ

- Матвей: рекомендация считается только если на фиксированном наборе 20–50 реальных задач стало лучше и ничего не сломалось; макс 1–3 правки за цикл; изменение графа/модели — через оунера. У нас `run-insights` делает rule proposals (хорошо), но: (а) bench сломан/не гоняется — нет fixed-set измерения «стало лучше», (б) нет механизма отката правила по метрике, (в) `lp.model-rebench` есть как граф, но не связан с принятием решений о смене моделей.
- Уроки → механизм: rule proposals существуют, но превращение урока в **чек/вороту** (не в текст) — ручное. У Матвея «держалось только то, что превращалось в механизм». Нужен путь lesson → proposed gate/check в воркфлоу, а не только → память.

## P2 — Управление поездом вживую

- Матвей: «в любой момент докинуть контекст, остановить, изменить; пауза→дискуссия→обратно в ту же ветку планирования». У нас: `rerunNode` (только terminal runs), wait/cancel, nudge. **Нет дешёвого "pause-and-resume same branch" для живого run** — пауза = cancel и перезапуск, не boundary-возврат в ноду. Engine это почти умеет (waiting steps + poll), но UX-пути «заморозить run, обсудить, вернуть» нет.

## P2 — Многоуровневый бюджет/DoD на волнах

- Бюджет есть на run; **общего бюджета на batch/wave** (Матвей: «волна с одним бюджетом, человек выпускает волну одним решением») нет — таски в run выпускаются по одному.

## P3 — «Неизмеренное ≠ ноль»

- Engine пишет usage per step (хорошо), но по Матвею неизмеренный расход должен отображаться как «not measured», а не отсутствовать. Проверить UI/репорты: неизвестный usage у скольких шагов скрывается.

# Что делать (порядок)

1. `writer-loopwatch` — детект активного цикла внутри хода (см. анализ выше).
2. Контракт проверки в задаче: обязательное поле `verify.command` в task → прогон до райтера (red gate) и после (clean copy) — механизм уже почти есть в verification.
3. Нода `substance-critique` после qa-gate + флаг «agent touched tests» через path-ownership.
4. Починить bench → fixed eval set для rule proposals и model-rebench (иначе самоулучшение без измерения).
5. Multi-level DoD: связать task→phase→run rollup (минимум: пункт DoD фазы = агрегат пунктов задач).

# Дополнено по полной выгрузке (1715 сообщений, 07.07–30.10)

## Граф одиночной задачи (картинка #22418, «версия 2, 03.09»)

`постановка → уточнение → дизайн(если нужен) → исполнение → проверка → приёмка → файл`

- **Уточнение** заполняет оркестратор: обещание списком, размер, нужен ли дизайн и почему; человек говорит «да» или правит. Пункты уточнения = **запускаемые проверки** + «что должно продолжать работать» (регрессия в контракте).
- **Проверка**: «база зелёная первым шагом + барьер: дифф + обещание; **другая модель — кодекс**». Проверяющий — другая модель, барьер = дифф + обещание (предсказание результата до старта).
- **«вернулое → следующий работник»** — красное возвращает задачу в очередь к ДРУГОМУ работнику, не тому же и не человеку.
- **Лимит — бюджет ступени, не счётчик**: «бюджет ступени превышен → вопрос человеку, не тихий стоп».
- **«пауза · стоп с откатом · поправка — на любой ступени»**.
- **«очередь: до подтверждения работнику не выдаётся»** — работник не видит задачу до подтверждения уточнения.
- Файл задачи `inline-<id>.md` пишется всегда при приёмке → «книга сделанного» (структура памяти).

## Ранняя пайплайн-роль (#17619, 28.07, лендосы)

контекстовик → ресерчер → планировщик (8–12 планов) → обзервер (что уже строил) → гриллер (независимо сверяет контекст+ресёрч с планом, «проверяет чтобы расхода не было») → строитель → верифаер (план-саммари, БЕЗ кода) → независимый проверяющий (план<>код) → UAT-обзервер по кнопкам. Одна страница ≈ 1,5–2 часа.

## 12 правил (файл #30844) — что держится только механизмом

- «Работает» = путь пройден целиком; на каждую связь — тест провода, не вычисления.
- Отложенная обязательная проверка — только в одном реестре со сроком, который дал человек; срок прошёл → проверка краснеет сама; агент срок не назначает и не продлевает.
- Остановка = подтверждённый выход И возврат работы, только потом удаление копии.
- Две одинаковые стены подряд — смени угол, вычисти весь класс, не один случай.
- Опасную команду судят по программе, которая реально запускается.

Наш afterMerge/turnedRed ≈ его стыки — это второй уровень, не дубль чистой копии.

Вывод «PM почти не выбирает граф сам» верен, но не «ноль раз». План: kind=process сначала спрашивает роутер, при confidence≥85 PM получает «это уже есть: граф X».

Графы ведут себя как тулы с описаниями: главный агент видит набор и берёт нужное. Значит у нас правильнее не «роутер подсовывает», а каталог как видимый реестр с качественными описаниями — PM выбирает сам, роутер-подсказка только дополнительный сигнал. Метрика: согласие с подсказкой И выбор без неё.
- Данные по чистой копии (thr_2pv7jua2pi, 31.10): 77 пост-слияния проверок, 0 turned red, 0 mainfix — класс «зелёное в worktree, красное в чистой» на 756 задачах не встречался. Решение: квитанция + HEAD-ревизия + счётчик uncommitted-файлов; включение clean-copy по сигналу (первая afterMerge-red ИЛИ запрос code-critic для задачи). Допущение триггера: committed-грязь (фикстура/хелпер под проверку) afterMerge не ловит — остаточно закрыто 1(а)-флагом и критиком.
- Research-док, стена 3 («"Stopped" has two conditions»): вышедший процесс ≠ вернувшаяся работа; остановленный ход не должен запускать продолжение; у него живую попытку судили как мёртвую и пересоздавали каждые пару минут. **У нас та же стена нашлась на хабе**: `errand:plugin_stopped` от выката записывался как провал повторяемого шага (убивал разведку magicseo). Фикс 0.1.415 — reentrant-шаг переживает рестарт и находит свой тред по ключу. И его урок «зелёное по двум каналам» подтвердился: ложный откат 0.1.414 из-за пересборки `app.*` хабом; второй канал — сверка `pluginVersion` в `app.meta.json`.

## Что это меняет в аудите

1. П0 остаётся: разложить writer-узел. Данные хаба (thr_2pv7jua2pi, 31.10): в 134/756 задач (18%) писатель правил эталонные тесты — code-critic видел 0 из них, предупреждение «the critic checks» врало. Детект существовал (`referenceTestEdits` + `test_fit` в finish.ts): удаление/ослабление ассерта уже блокирует приёмку (`assertion_removed`, `assertion_weakened`, `skipped`, `expected_changed`, `verification_narrowed`), но «тихая» правка без паттерна — только warning, а критик решался раньше и по риску. Фикс 0.1.414: эталонные тесты считаются ДО решения о критике, их наличие включает code-critic в gate-режиме при любом риске, rework → repair-раунд с выводом критика, сверх max_rounds → блок. Оставшиеся края: флаг — только TEST_PATH (чек-скрипты .sh/.yml в testEdits не входят), caps slice(0,20)/readFit-400-строк; «следующий работник» и «бюджет ступени» отложены на шаг узлов. Уточнение: у Матвея «проверка» — отдельный узел с **другой моделью** и барьером «дифф + обещание», а не пост-обработка в том же исполнителе. У нас verification в worktree самого писателя (thr_2pv7jua2pi подтвердил: стадия есть, но не в чистой копии; code-critique 9% и advisory).
2. «вернулое → следующий работник»: при возврате из проверки задача уходит не тому же агенту — стоит зафиксировать как правило для rework-узла.
