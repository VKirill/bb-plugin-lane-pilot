### 4.2 Confirmed contradictions by product area

<a id="f-001"></a>

#### F-001 — Проверки задачи переигрываются после уже зелёного прогона

| | |
| --- | --- |
| Evidence | CONFIRMED-CODE |
| Severity | P1 |
| Confidence | high |
| Parent | T-002 / S-004 |
| Scope | Каждая кодовая задача с `verification[]` без секретов, у которой worktree вливается в базу |

**Обещание.** Этап `verification` решён, когда каждая команда из `verification[]` вышла с кодом 0 (`packages/contracts/src/stage-proof.ts`, поле `verification`).

**Противоречие.** После того как кандидат уже принят по этим кодам, `finish.ts` делает ещё два круга. `runPlanFactStage` снова сверяет те же `exitCode` и дифф. Затем `gitIntegrate` получает `replayChecks` — те же команды, до 20 штук, с таймаутом не меньше того, на котором они уже прошли (`src/rooms/writer/server/finish.ts`, блок `replayChecks`). Комментарий в этой функции сам называет живой простой: Vampirism Fire, 2026-10-25, `vf-s7-cosmetics` и `.2` «застряли» на 47–63 минуты, каждая в 7–18-минутном повторе `studio_test` после зелёных проверок. Если включена критика кода, каждый круг починки ещё и заново вызывает `validateWriterResult`.

**Следствие.** Задача, которая уже зелёная, стоит в очереди вливания и выглядит для сторожа как «проверка ещё идёт». Quick этот повтор не выключает: `applyQualityMode` трогает только флаги критики.

**Воспроизведение (по коду, рантайм не гонялся).**

1. Задача с непустым `verification[]` без `secrets`.
2. Писатель проходит проверки, кандидат `accepted`.
3. `shouldMergeAttemptWorktree` истинен.
4. В `gitIntegrate` уходит `replayChecks` из тех же команд.

Ожидание по тексту доказательства этапа: exit 0 один раз достаточен. Факт: те же команды ставятся снова перед вливанием.

Повтор в этой сессии не делался. Инцидент 47–63 мин — запись авторов в комментарии, не замер этого аудита.

**Доказательства.** [evidence/stage-and-lane.md](evidence/stage-and-lane.md). `finish.ts` около строк 645–665 и 752–778. `stage-proof.ts` строки 33 и 36.

**Контрдоказательство.** Повтор при сдвинутом main имеет смысл: база уехала, пока задача работала. Код не отличает «main не двигался» от «переиграть всё». Секреты из повтора исключены — это не отмена круга, а дырка в нём.

**Причина.** Повтор зашит в приёмку вливания, а не в отдельный случай «база изменилась».

**Починка.** Переигрывать команды только если head базы сдвинулся после прогона писателя. Иначе брать уже записанные коды выхода.

**Приёмка.** Задача с зелёными проверками и неподвижным main вливается без второго запуска тех же команд. Тест падает на текущем дереве, если `replayChecks` уходит при неизменном head.

Прожарка: [F-001] Проверка сдала экзамен, и её тут же сажают пересдавать тот же билет, пока очередь на вливание делает вид, что работа ещё идёт.

#### F-002 — Критика плана по умолчанию — ворота, хотя в реестре это мнение

| | |
| --- | --- |
| Evidence | CONFIRMED-CODE |
| Severity | P1 |
| Confidence | high |
| Parent | T-001 / S-001, S-002 |
| Scope | Любая задача при непереопределённых настройках проекта (`quality_mode` standard) |

**Обещание.** `plan-critique` в `STAGE_PROOF` — `advisory`: вердикт модели. `acceptanceProofGap` прямо говорит, что мнение не принимает задачу. Обзор продукта повторяет: четыре этапа-мнения, среди них `plan-critique` (`docs/overview.md`).

**Противоречие.** Незаданная настройка читается как включённая критика в режиме `gate` (`src/rooms/core/server/core.ts`, ключи `plan_critique.enabled` и `plan_critique.mode`). Граф при `allowed === false` идёт в `block-plan-critique` и блокирует попытку до писателя (`workflows/lp-task-pipeline.json`, `dispatch-workflow.ts`). Режим `advisory` в рантайме есть, но это не значение по умолчанию: по умолчанию мнение — стоп-кран до первой строки кода.

Quick честно выключает эту критику и критику кода (`quality-mode.ts`). Дальше граф всё равно заходит в узел `plan-critique-quick` (тот же `lp.plan-critique`), затем в specialist, базу владения и папку задачи. Specialist от `quality_mode` не зависит (`shouldRunSpecialist` смотрит только свой тумблер; по умолчанию он выключен). Фраза при закрытии фазы обещает, что мелкая работа «проходит этапы быстро» (`driver.ts`). Повтор проверок из [F-001] эта фраза не отменяет.

**Следствие.** Обычная задача не стартует, пока модель не разрешит план. Мелкая задача в quick всё равно платит за обход графа и за повтор проверок при вливании.

**Воспроизведение.**

1. Проект без `plan_critique.*`.
2. Диспатч задачи не в `quality_mode=quick`.
3. Критик возвращает отказ.

Ожидание по реестру доказательств: мнение не решает приёмку. Факт: попытка `blocked`, писатель не стартует.

**Доказательства.** `core.ts` около строк 303–304. `stage-proof.ts` строки 27–28 и 55–60. `dispatch-workflow.ts` `lp.block-plan-critique`. `quality-mode.ts` строки 1–25. `driver.ts` около строки 577.

**Контрдоказательство.** Ворота до кода ловят план без владельца путей — это отдельная структурная проверка внутри критика, не вердикт модели. Её можно оставить коду. Отключённый specialist на quick не зовёт модель: узел есть, вызов дешёвый. Это не отменяет ворота по умолчанию.

**Причина.** Реестр говорит «мнение», дефолт настроек говорит «gate», граф слушает дефолт.

**Починка.** Дефолт `plan_critique.mode` — `advisory` (вердикт пишется, писатель стартует), либо реестр честно помечает этап как `gate`, когда режим gate. Quick не должен обещать скорость, пока [F-001] жив.

**Приёмка.** На чистом проекте отказ критика плана не переводит попытку в `blocked`. Структурная ошибка контракта (цикл `depends_on`, чужой путь) по-прежнему блокирует без модели.

Прожарка: [F-002] В паспорте этапа написано «это всего лишь мнение». На двери по умолчанию висит «без подписи модели внутрь не пускаем».

#### F-003 — Включённый PM-read останавливает задачу, хотя доказательство говорит, что он ничего не решает

| | |
| --- | --- |
| Evidence | CONFIRMED-CODE |
| Severity | P2 |
| Confidence | high |
| Parent | T-001 / S-003 |
| Scope | Только проекты с `pm_read.enabled` (в UI запасное значение — выключено) |

**Обещание.** Текст доказательства: сводка «только передаёт контекст критикам и ничего не решает» (`stage-proof.ts`, `pm-read`). Пустая сводка валит этап по форме, не по сути работы.

**Противоречие.** Пустой вывод, таймаут или неразобранный JSON дают `state: "failed"`. Ребро графа ведёт в `lp.block-pm-read`: попытка `blocked`, ран `blocked`, этапы писателя помечены пропущенными (`dispatch-workflow.ts`). Тест называет это ожиданием: «PM read returns malformed output: blocked» (`tests/workflow/equivalence.test.ts`). Комментарий в `pm-read.ts` уже помнит, как лишний ключ Haiku остановил целую задачу; лишние ключи выкинули, а провал сводки по-прежнему стоп.

**Следствие.** Включённая «читалка контекста» может не пустить писателя из-за кривого JSON. Пока тумблер выключен, путь молчит — поэтому не P1.

**Воспроизведение.** Включить `pm_read.enabled`, дать `read_first` длиннее порога (дефолт 350 строк), вернуть не-JSON. Ожидание по тексту доказательства: контекста нет, задача идёт дальше. Факт: `pm_read_failed`, писатель пропущен.

**Доказательства.** `stage-proof.ts` строки 25–26. `critique-runs.ts` `runPmRead` ветка `catch` и порог строк. `dispatch-workflow.ts` `lp.block-pm-read`. `pm-read.ts` строки 27–30.

**Контрдоказательство.** Ниже порога строк этап честно `skipped` и не блокирует. Выключенный тумблер тоже skip. Блок — только включённый этап плюс ошибка модели.

**Причина.** Граф считает `failed` у рекомендательного этапа поводом не писать код.

**Починка.** Провал PM-read записывать как skipped с причиной и идти в критику/писателя без сводки. Блокировать задачу он не должен.

**Приёмка.** При включённом PM-read и мусорном ответе модели попытка не `blocked`, писатель стартует, в квитанции причина пропуска.

Прожарка: [F-003] Конспект, которому по уставу нельзя решать, при плохом почерке отменяет урок.

#### F-004 — Claude Lane вшит как второе изделие

| | |
| --- | --- |
| Evidence | CONFIRMED-CODE |
| Severity | P1 |
| Confidence | high |
| Parent | T-002 / S-005 |
| Scope | Тест карты SMA; нативная сессия; писатель OpenCode; квитанция приёмки |

**Обещание.** Плагин оркестрирует изолированные задачи в BB (`package.json`: «Isolated Lane Stack PM in BB and native writer dispatch»). Lane Stack — сосед, не тело плагина.

**Противоречие.** Четыре независимых способа тащить соседний репозиторий в каждый шаг.

1. Карта SMA: 1798 узлов и 2654 рёбер обязаны сойтись, и каждый proof-путь должен существовать (`tests/sma-map.test.ts`). Корни включают `~/tools/claude-lane-stack` и ядро `bb-source-vk`. В `entries.ts` 377 записей вида `lane-stack:…`. Шапка файла сама говорит: ссылка — навигация, не проверка поведения. Тест всё равно падает, если символ в соседнем репозитории переехал.
2. Нативная сессия пишет `guard_shell.py` из бандла (копия хуков Lane Stack) и, если проект сам не повесил этот файл на `*`, вешает его на каждый инструмент (`native-session-hooks.ts`). `bb-shim.ts` требует держать список запретов равным `_bb_args_error` в `lane-stack/hooks/guard_shell.py`. `reconcileClaudeLane` ещё и переустанавливает плагин `lane-stack@claude-lane-stack` и доверяет хуки Codex.
3. Квитанция приёмки валидируется схемой `lane-stack/schemas/acceptance-v2.schema.json` (`stage-proof.ts`, `acceptance-receipt`).

## 5. The roast

[F-002] Обычная задача в этом плагине начинается не с кода, а с разрешения модели. В реестре этапов критика плана подписана как мнение. В настройках по умолчанию то же мнение — ворота: не пустили, писатель даже не сел. Паспорт и дверь живут в разных зданиях.

[F-001] Когда писатель всё-таки прошёл свои команды, плагин делает вид, что не расслышал. Те же команды ставятся в очередь вливания ещё раз. Авторы уже оставили в коде памятку: две задачи полчаса–час «висели» на повторе теста, который только что был зелёным. Quick этот повтор не трогает. А фаза, если её попытаться закрыть раньше рельсов, утешает: заведите один-два куска, этапы пройдут быстро. Быстро здесь значит «ещё один полный круг».

[F-003] Отдельно стоит читалка файлов. Ей написали в доказательстве этапа: ничего не решаешь. Включили её — и кривой JSON отменяет задачу целиком. Пока тумблер выключен, она молчит. Это не делает подпись честной.

[F-004] Claude Lane в плагине не библиотека функций. Это второй продукт, который надо кормить. Карта на 1798 узлов считает «у нас это есть», если в соседнем репозитории находится строка. Тест падает, когда сосед переименовал функцию. Сессия писателя получает стража на каждый инструмент, список запретов надо держать в двух местах, приёмка сверяется с чужой схемой, а перед стартом ещё до трёх четвертей минуты выбираются дополнительные скиллы поверх двух, которые и так всегда в роли. Один раз файлы самого стека уже записали на счёт писателя.

[F-005] Пока коридор пересдаёт тест, в здании нарисован офис с деревьями. Рисовать можно. Нельзя называть это устройством работы.

[F-006] Это не опечатка одного файла. Python-конвейер до сих жив и на строке 218 пишет критике `advisory`. TypeScript, который его сменил, в пустую клетку подставляет `gate`. Каталог из 481 настройки тычет в питон и объявляет дефолтом `gate`. Две программы, один ключ, два смысла.

[F-007] После того как узкая проверка сдана и пересдана, плагин осматривает папку проекта, находит `npm test` и запускает весь набор, хотя владелец ворота не включал. Если набор умер по таймауту, код собирает вторую команду и ставит её снова. Фраза «один раз на пачку» считает плохо.

[F-008] Плагин Claude Lane в своём `plugin.json` всё ещё «сольный PM». На старте сессии он до десяти минут поднимает сайдкар winnow. На каждый промпт зовёт skillranker. Поверх этого `guard_shell.py` на две тысячи строк знает роли Lane Pilot по именам. Оркестр один, дирижёра объявили дважды, и оба машут.

[F-009] Когда этот клубок ломается, самопочинка включена сама и до четырёх раз в день посылает агента чинить оркестратор. В промпте написано не трогать ту копию стража, которую установка Claude как раз и кладёт в настройки. Чинится запасной ключ.

Вместе по обоим репозиториям: задача проверяется мнением до старта, узкой командой, повтором той же команды, полным набором и иногда повтором полного набора. Параллельно второй плагин проверяет сессию своими хуками. Готовность кода меряется картой на 1798 узлов. Рантайм этого прохода не подтверждался.
