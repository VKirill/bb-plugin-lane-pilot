# Memory conflict management

TL;DR: Memory conflict management detects deterministic disagreements between notes, registers them in SQLite, and holds both notes invisible to all readers until human settlement.

## Purpose

The conflict management subsystem prevents conflicting or contradictory facts from circulating among agents by detecting contradictory statements across active notes, holding disputed notes in SQLite, and suppressing them from all search queries until resolved by human operators (`packages/memory-core/src/conflicts.ts:3-16`, `packages/memory-core/src/conflict-store.ts:5-15`).

## How it works

1. Pairwise note evaluation: `findConflicts` iterates through active project notes pairwise; each pair is ordered with the older note as `a` and the newer note as `b` (`packages/memory-core/src/conflicts.ts:95-105`).
2. Subject matching: `sameThing` evaluates whether two notes share the same subject (`packages/memory-core/src/conflicts.ts:58-66`):
   - Compares file paths extracted via regex: if both notes mention the same repository file path containing a `/`, that path is the subject (`packages/memory-core/src/conflicts.ts:60-61`).
   - If no common path exists, compares non-generic concepts (excluding tags like `"invariant"`, `"review"`, `"pitfall"`, `"security"`, `"regression"`, `"test"`, `"gotcha"`): returns the concepts if they share at least 3 tags representing >= 50% of both notes' concept sets (`packages/memory-core/src/conflicts.ts:62-65`).
3. Disagreement classification: `disagreement` analyzes the candidate pair for three deterministic conflict patterns (`packages/memory-core/src/conflicts.ts:69-92`):
   - Numeric quantity mismatch (`kind: "value"`): `quantities` parses label words preceding numbers and units (such as `ms`, `s`, `min`, `h`, `kb`, `mb`, `retries`, `tokens`). If two notes share identical labels and units but report different numbers, a value conflict is reported (`packages/memory-core/src/conflicts.ts:38-47, 72-75`).
   - Constant or literal mismatch (`kind: "literal"`): `literals` identifies patterns like `IDENTIFIER = value` or `key: value`. If both notes share the identifier name but have different string values, a literal conflict is reported (`packages/memory-core/src/conflicts.ts:50-56, 76-79`).
   - Statement polarity inversion (`kind: "polarity"`): `sentences` splits content into sentences; checks pairs where one sentence contains negation terms (such as `not`, `never`, `cannot`, `не`, `нет`, `без`) and the other does not. If non-negation words share >= 80% Jaccard similarity, a polarity conflict is reported (`packages/memory-core/src/conflicts.ts:80-90`).
4. Stability check during writes: when `storeMemoryRecords` processes a replacement for an active note, it checks if the older note was used or accepted in briefs within the last 30 days (`STABLE_MS = 30 * 86_400_000`) (`packages/memory-core/src/store.ts:162-163`). If recently used, it calls `holdConflict` instead of silently replacing the note (`packages/memory-core/src/store.ts:164-173`).
5. Recording held conflicts: `holdConflict` inserts a row into `lane_pilot_memory_conflict` with `state = 'held'` and a deterministic ID generated by `conflictId(a, b)` (`packages/memory-core/src/conflicts.ts:108`, `packages/memory-core/src/conflict-store.ts:68-76`).
6. Query suppression: `heldClause` appends a SQL `NOT EXISTS` condition to all search queries, matching `lane_pilot_memory_conflict` where `state = 'held'` and the note ID equals `note_a` or `note_b` (`packages/memory-core/src/conflict-store.ts:62-65`, `packages/memory-core/src/store.ts:309`). Both notes become invisible to search and context packing (`packages/memory-core/src/conflict-store.ts:7-9`).
7. Settlement: human operators inspect held conflicts via `listConflicts` / `getConflict`, optionally link an owner deferral item via `setDeferral`, and settle the conflict using `markSettled` with an explicit resolution (`keep_a`, `keep_b`, `keep_both`, `drop_both`, `moot`) (`packages/memory-core/src/conflict-store.ts:78-96`).

## Modes, variants and branches

| Conflict kind / State | Detection criteria | Registered evidence | Effect on readers | Evidence |
|---|---|---|---|---|
| Value conflict (`kind: "value"`) | Shared subject, identical label and unit, differing numeric value | Matched quantity phrases from both notes | Both notes held; suppressed from search | `packages/memory-core/src/conflicts.ts:72-75` |
| Literal conflict (`kind: "literal"`) | Shared subject, identical identifier name, differing literal value | Matched identifier assignments | Both notes held; suppressed from search | `packages/memory-core/src/conflicts.ts:76-79` |
| Polarity conflict (`kind: "polarity"`) | Shared subject, sentence Jaccard >= 0.8 with opposite negation parity | Opposing sentences (up to 200 chars) | Both notes held; suppressed from search | `packages/memory-core/src/conflicts.ts:80-90` |
| State: `held` | Initial state upon detection | Stored in `lane_pilot_memory_conflict` | Notes suppressed via `heldClause` | `packages/memory-core/src/conflict-store.ts:27, 62-65` |
| State: `settled` | Updated after human or owner decision | Resolution and settlement timestamp stored | Notes no longer held; unblocked or updated per resolution | `packages/memory-core/src/conflict-store.ts:27-28, 94-96` |

## Failure behavior

| Failure condition | Handling mechanism | Outcome | Evidence |
|---|---|---|---|
| Conflict table not initialized | `conflictTableReady` checks SQLite master | Returns `false`; `heldClause` returns empty string | `packages/memory-core/src/conflict-store.ts:51-64` |
| Duplicate conflict insertion | Handled by `INSERT OR IGNORE` in `holdConflict` | Ignores duplicate; leaves existing conflict row unchanged | `packages/memory-core/src/conflict-store.ts:72` |
| Settling non-held conflict | `markSettled` checks `WHERE state='held'` | Returns `false` (zero rows updated) | `packages/memory-core/src/conflict-store.ts:94-96` |
| Unknown resolution value | SQLite table constraint `CHECK(resolution IN (...))` | Transaction throws if invalid resolution passed | `packages/memory-core/src/conflict-store.ts:28` |

## Business rules

- Hold both rule: when a contradiction is detected, both notes are held rather than picking one or tagging them with uncertainty markers (`packages/memory-core/src/conflict-store.ts:11-13`).
- Budget retention: held notes retain `status = 'active'` in storage so their tokens continue counting against budgets (`packages/memory-core/src/conflict-store.ts:8-10`).
- Deterministic conflict identity: `conflictId` (`packages/memory-core/src/conflicts.ts:108`) formats deterministic IDs so discovery order does not produce duplicate rows in `holdConflict` (`packages/memory-core/src/conflict-store.ts:68-76`).
- Thirty-day stability window: a note used or accepted within 30 days (`STABLE_MS = 30 * 86_400_000`) cannot be silently superseded by a new candidate; its replacement triggers a conflict hold (`packages/memory-core/src/store.ts:162-171`).
- Permitted resolutions: valid conflict resolutions are strictly `keep_a`, `keep_b`, `keep_both`, `drop_both`, or `moot` (`packages/memory-core/src/conflict-store.ts:28, 38`).

## Public API or commands

- `findConflicts(notes, only?)`: scans notes pairwise and returns detected conflicts (`packages/memory-core/src/conflicts.ts:95-105`).
- `disagreement(a, b)`: checks whether two notes disagree and returns the conflict classification (`packages/memory-core/src/conflicts.ts:69-92`).
- `sameThing(a, b)`: determines if two notes refer to the same subject path or concepts (`packages/memory-core/src/conflicts.ts:58-66`).
- `quantities(text)`: extracts number-unit pairs with contextual labels (`packages/memory-core/src/conflicts.ts:38-47`).
- `literals(text)`: extracts identifier-value pairs (`packages/memory-core/src/conflicts.ts:50-56`).
- `conflictTableReady(db)`: checks if conflict tables exist in the database (`packages/memory-core/src/conflict-store.ts:51-56`).
- `heldClause(db, alias)`: returns SQL fragment to exclude held notes from queries (`packages/memory-core/src/conflict-store.ts:62-65`).
- `holdConflict(db, input)`: inserts or updates a held conflict row (`packages/memory-core/src/conflict-store.ts:68-76`).
- `getConflict(db, id)`: retrieves a conflict record by ID (`packages/memory-core/src/conflict-store.ts:78-81`).
- `listConflicts(db, filter)`: lists conflicts by project or state (`packages/memory-core/src/conflict-store.ts:83-88`).
- `setDeferral(db, id, deferralId)`: links a conflict to an owner deferral item (`packages/memory-core/src/conflict-store.ts:90-92`).
- `markSettled(db, id, resolution, evidence, now)`: updates conflict state to settled with chosen resolution (`packages/memory-core/src/conflict-store.ts:94-96`).

## Gotchas

- Held notes are silently excluded from all search and export queries; neither the querying agent nor the caller receives an error or warning indicating that relevant information was suppressed due to an unresolved conflict (`packages/memory-core/src/conflict-store.ts:7-9, 62-65`, `packages/memory-core/src/store.ts:309`).
- `findConflicts` performs a pairwise comparison ($O(n^2)$) across all notes in a project; while bounded in practice by note budgets, calling it with thousands of unindexed notes can introduce latency (`packages/memory-core/src/conflicts.ts:94-98`).
- Near-identical restatements of a note do not create conflicts because `sameSubject` supersedes the older wording at insertion time before conflict detection runs (`packages/memory-core/src/conflicts.ts:12-13`, `packages/memory-core/src/store.ts:187`).
