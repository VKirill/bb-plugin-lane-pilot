- **The guard reads the hub in every notation `ssh` reads.** `ssh|scp|sftp|rsync|mosh|autossh` to the hub was matched against the literal strings `10.8.0.1` and `54.37.129.153`. `guard_shell.py` now turns each host-looking word into a number (`10.8.1`, `10.524289`, `0x0a080001`, `168296449`, `012.010.0.1`, `10.0x8.0.1`, a trailing dot, the public address as a number or hex) and reads IPv6 forms that carry an IPv4 address (`::ffff:10.8.0.1`, `::ffff:a08:1`, `0:0:0:0:0:ffff:a08:1`, `[::ffff:10.8.0.1]:path`, upper case, `64:ff9b::` and `::a.b.c.d`); it takes the host out of `user@host`, `host:path`, `ssh://`, `-o HostName=`, `-J a,b` and a hop inside a quoted remote command; an alias of `~/.ssh/config` is followed to its `HostName`; a dotted name is looked up and refused when it resolves to the hub (at most 6 lookups, 1.5 s each, a name that does not answer in time is not refused; names that are local files and numeric names are not looked up). `rescue-vps` joins the hub names. The PM still reaches the hub.
- **Wrapper options that take a value no longer hide `bb`.** `sudo -u root bb ...`, `env -u X bb ...`, `env -C dir bb ...`, `timeout -s KILL 5 bb ...`, `exec -a x bb ...`, `nice -n 5 bb ...`, `xargs -I{} bb ...` took the value for the command. The wrapper list now knows which options take a value, and `env -S 'bb ...'` / `--split-string=` is read as a command line. The file `BB_CLI` points at counts as `bb` whatever it is called. (A path ending in `/bb`, `command -p bb`, `env bb` and `node .../bb` were already caught by the guard; they pass only the PATH wrappers, which cannot see them.)
- **Schedule writes and the anamnesis are in all three lists.** The shell guard already refused `schedule_upsert|delete|pause|resume|run_now|cancel_run` and `bb lane-pilot schedule create|update|delete|pause|resume|run-now|cancel-run`; the PATH wrappers (`src/bb-shim.ts`) and the OpenCode `permission.bash` deny list (`OPENCODE_BASH_DENY`) did not, so a Codex, Cursor or OpenCode writer could create a script schedule. The anamnesis: the RPC `anamnesis` (one method for every op, including sensitive reads and `forget all`) is refused for every Lane Pilot agent, `bb lane-pilot anamnesis <anything>` for every agent but the PM, and for the PM the writes `add|edit|confirm|reject|forget`, `sources --set`, `config --authors|--roots`, `load --run` and a subcommand the guard cannot read; the PM keeps `status|list|show|history|whoami|card|review|host` and the plain `sources`, `config`, `load` (plan).

Learning from the owner's messages (design of 2026-10-08, T1-T8; src/learning).

- **T1+T2: every message of the owner is judged where he says it, in observation mode first.** `src/learning` subscribes to the owner-message hub of the anamnesis room (`createOwnerMessageHub`, one collector for both layers), and a live feed fills the hub: BB's `thread.active`, `thread.idle` and the debounced `experimental_thread.events` make it read the thread's newest `client/turn/requested` events (one read of five events, at most one per 3 s per thread; writer, helper and plugin threads are dropped before any read). For each message Jev (`learning.owner_message`, version 1) answers five questions in one request (kind of message, worth remembering, reach, annoyance, a date or promise) with the agent's previous reply as context, and the shared Jev receipt keeps the answers without the text. The route is `learn` / `none` / `contested`; a contested message (0.35 to 0.6), a message Jev cannot answer, and a 10 % sample for the agreement report also go to OpenAI Decisions (`gpt-6-luna`, key `OPENAI_API_KEY` read from the Env Catalog by name, never logged), which answers the same questions; one says learn and the other none sends the message on. A sensitive message (health, family, money, documents, clients) goes to Jev only. Personal data is masked before anything leaves (`maskPii`). `lane_pilot_learning_obs` holds one row per message (judgments, a 280-character masked excerpt, no body unless the extractor needs it); `observe` mode (the default) records and does nothing else. Costs and caps are settings of the room (`learning:config`): `sample`, `dailyJudgeCap` 300, `secondOpinionDailyCap` 60, `agreeSample` 0.1. A Jev request is about 1.1k tokens a message; the second opinion is 200 ms and $0.10 per million input tokens (a hundred of them are about one cent). `bb lane-pilot learning status|review|label|agreement|config` and the PM action `lane_pilot_memory {action:"learned"}` show the evidence for switching to `active`: a week of observation, 50 messages checked by hand at 80 % or better, the agreement of the two judges, the cost.
- **T3: a short model draws the lasting thing out of the messages that taught something, and code routes it.** In `active` mode a message the judges sent on keeps its masked text (a day at most) until the extractor reads it: every 30 minutes a project with a message waiting for 10 minutes, or five of them, gets one run of the project's rules analyzer model (a hidden thread, `rulesAnalyzer` selection, default Codex GPT-6 Luna) on up to 12 messages, six runs a day. The model answers JSON (`nothing` is valid; a rule, a preference, a decision, a date or a fact, each with the message it stands on). Code checks the answer and compares each statement with what is in force (a cheap word comparison first, then Jev `learning.same_as`: same, opposite or different): a repeat adds a confirmation (`occurrences` of the rule), a contradiction is held for the owner, a new project rule or preference goes on trial as a rule of Lane Pilot (`audience` pm, writer or both, through `upsertLessonProposal` and `adoptRuleProposal` like the PM's `lane_pilot_lesson`), a decision becomes a note in the project's memory, an owner-wide preference and a date wait for his yes, a fact is only recorded. `lane_pilot_learning_item` refuses a row without its message (`evidence`). `op:"accept"|"reject"|"drop"` decide: accepting a global preference returns the `bb memory add` command to run (BB gives an agent no other way to add a memory), a date becomes a reminder in the thread it was said in, a contradiction retires the old rule and puts the new one on trial. `createRuleScan` now also returns `runAnalyzer`, which the extractor reuses.
- **T4: the rules for the PM reach the PM, and a pool of rules has a budget in tokens instead of twelve places.** The map of 2026-10-08 found that rules written for the PM (`audience` pm or both) were read only by writers and the rule scan; the PM saw one only by searching memory. A PM that starts now has its project's rules in its prompt (`pmRulesPromptBlock` in `activation.ts`), in the order always-on, confirmed or the owner's, then on trial newest first, within `pmRulesTokens` (1600), never cutting a rule and saying how many did not fit; `lane_pilot_memory {action:"learned", op:"rules", text}` picks the ones that apply to a text with Jev (`learning.pm_rule_relevance`, p(yes) 0.06 as for the writers' rules). `adoptRuleProposal` no longer stops at `RULE_TRIAL.maxActive = 12` a pool (319 refusals on the hub): a rule fits when the pool's tokens plus its own are within the budget (`pmRulesTokens` for the PM pool, `writerRulesTokens` for the writers', a ceiling of 60 rules against runaway growth), and a rule that does not fit takes the places of as many of the weakest rules on trial (three days old at least) as it needs; if the confirmed, the owner's and the young cannot make room, nothing is retired and the journal says so (`cap_reached` with the tokens). A project whose core memory budget (`memory.core_budget`, 3072 tokens, shared with the maintainer's conventions) is full gets the same journal line instead of a failed tool call. Raising `memory.core_budget` is the way to give a busy project more rules than the shared budget allows.
- **T5: a daily «what I learned» report, answered in the chat, with no form.** At 18:20 each project that has new learned items gets one message in its open PM chat (`composeDigest`): what is now in force (rules on trial, decisions noted), what waits for a yes or no (an owner-wide preference, a date, a statement that contradicts a rule in force), and how the PM answers (`lane_pilot_memory {action:"learned", op:"accept"|"reject"|"drop", id}`). The PM tells the owner in its own words and asks the waiting questions like any other question; nothing global is written before the owner's yes. An item is announced once; without an open PM chat it waits for the next day; at most 10 are listed, the rest by `op:"items"`. Only in `active` mode. `bb lane-pilot learning digest` composes it without sending; `--send` sends it.
- **T6: clear annoyance of the owner becomes an incident for the self-repair watcher.** When Jev reads a message as «clearly frustrated» (p at least 0.5; the second opinion decides when Jev cannot answer) the room records it in observation mode as a signal, and in `active` mode writes a record in the key-value store (`learning:frustration`: thread, a masked quote of at most 240 characters, the tail of the agent's reply, the PM thread and run; one a day for a thread, the last 50 kept). `collect` in the self-repair watcher reads it like the output guard's list and files an incident of kind `owner` (severity 3) whose reason asks the repair engineer to find what Lane Pilot did or failed to do, fix it if it is Lane Pilot's, and otherwise change no code and tell the PM. A sensitive message gives an incident without its text.

### Env Catalog (phase J)

Secrets for checks, browser logins and deploy steps, from BB's Env Catalog, with least privilege. Needs the `env-catalog` plugin for any of it; without it a task that declares nothing is unaffected.
- **J1, roles.** Env Catalog tools go to the roles that use them: errands and the four specialists (design-lead, copy-lead, seo-specialist, tavily). A writer has none, and its brief no longer promises `env_get` (it says its checks get declared secrets as environment variables and it never sees a value). The browser-check thread gets Env Catalog only for a case that names a login (J5).
- **J2, secrets in checks.** `verification[].secrets: [NAME]` per check (Env Catalog kind secret or login). The contract lint checks the names: a typo of a saved name, an ssh/ftp kind, a sandbox variable name, a name the owner has not allowed and an absent Env Catalog send the task back; a name that is simply not saved yet is a warning (the task waits, J6). The server reads the values through `env_get_value` only for the check that declares them and passes them as the sandbox's environment (`runSandboxedCommand` takes `env`; bwrap gets them in its own environment, never in its arguments). A check with secrets runs through the host call, not a BB terminal and not a stored background job, and is left out of the host's replay before a merge (the post-merge check on main still runs it). A login expands to `NAME_USERNAME`, `NAME_PASSWORD`, `NAME_URL`.
- **J3, masking.** `src/redact.ts` masks every value handed out (plain, JSON-escaped, URL-encoded, base64, each line of a multi-line key) as `***`: on the host in the check's output, again on the server, in `cleanCheckOutput` (retry briefs, task-folder logs, failure reasons), in the plugin log, in a browser check's verdict and in an errand's report.
- **J4, least privilege.** Project setting `secrets.allow` (owner-only, empty means none): only names listed there are handed to a check, a browser login or an errand, and only when the step declares them. The PM cannot change it.
- **J5, browser logins.** A case starts with `login: NAME` (kind login). Nothing starts unless the login exists and is allowed (the answer says what to do and no stage is recorded); the check thread's profile adds Env Catalog for that run only, and its prompt names that one account.
- **J6, waiting for access.** A task whose checks need a missing or not-yet-allowed name waits before any writer starts (stage reason `waiting_secret:NAME`, class contract, no attempt spent); the PM is told once to call `env_request`; the wait ends by itself when the access is in place (polled every 20 s: BB's `env-catalog:changed` signal reaches the app only, not a plugin's server) and gives up after 12 hours. A secret lost mid-task parks the task (the 5-minute sweep restarts it, a day at most).
- **J7, deploy access.** `lane_pilot_errand` takes `accounts: [NAME]` (any kind, allowed names only): the helper is told to read them from Env Catalog, to keep an SSH key in a temporary folder outside every repository and delete it, and its report is masked.

## 0.1.116

Stability, after the 2026-10-04 incidents and a survey of how merge queues, workflow engines, CI and agent harnesses handle failures (`.bb/chats/thr_tev4nistgf/artifacts/failure-practices/REPORT.md`).

- **Failure classes** (`src/failure-class.ts`): every failed attempt is task, provider, merge, harness (Lane Pilot's fault), infra (machine), contract or judgment. The PM gets one message listing what was parked and restarted (Temporal, Step Functions redrive, SQS redrive).
- **Project breaker:** three tasks failing on the same Lane Pilot fault within 15 minutes hold the project's new writers until the fix ships, letting one through after 30 minutes.
- **Disk guard:** a writer waits while its host has less than 15 GB or 5% free (new host call `diskFree`).
- **Stale git lock:** before a merge and before creating or removing a worktree, an `index.lock` older than 60 s with no live holder is moved aside.
- **Flaky checks:** a failing verification command runs once more; passing on the re-run counts as passed with `flaky: true`. A command killed by its time limit is not re-run (the host sandbox now reports a timeout as exit 124).
- **Contract checks before a writer:** `output_binary` (warning) for fonts, images, archives a model cannot author; `verify_filter_ignored` (error) for `npm -w <ws> run test -- <filter>` when the script is `node --test`, which ignores the filter; `depends_self` and `depends_cycle` (errors).

- **Rules carry their reasons.** One docs rule with its reason («Lane Pilot writes docs nightly and reverts other edits») for every session; reasons for the PM's autonomy, the shell-edit ban and the specialists' former bare prohibitions; the list of agents the PM may not spawn is gone because code already strips them.

- **Night review blocks only on real defects**: a concrete unmet requirement, broken behavior, a security or data-loss risk; style is a warning at most.
