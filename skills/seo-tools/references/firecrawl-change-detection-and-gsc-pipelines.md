# FireCrawl + n8n + GSC: конвейеры сбора, мониторинг конкурентов, выгрузки Search Console

> [!NOTE]
> Инженерный синтез по материалам Q1 2026 (автор курса — Максим Котёнков). Пересказ и выводы собственные; цифры
> взяты из уроков и помечены, если это оценка или расширение. Метка `[VERIFY]` — проверить по актуальной документации
> провайдера перед тем, как зашивать значение в узел графа.

## 1. Принцип: одна точка интеграции — HTTP Request + JSON-тело

Готовые community-ноды для FireCrawl и Search Console отстают от API и урезаны. Рабочая архитектура для графов:

| Слой | Решение | Почему |
|---|---|---|
| Транспорт | Один HTTP-клиент, метод POST, JSON-тело | любой новый параметр API доступен сразу |
| Авторизация FireCrawl | Заголовок `Authorization` со значением `Bearer fc-…` (Header Auth) | одна credential на все эндпоинты |
| Авторизация GSC | Google OAuth2 (общая), scope `…/auth/webmasters` | отдельной ноды GSC нет; с января 2026 пустой scope отвергается |
| Генерация тел запросов | LLM, которой отдана документация (NotebookLM/Ask AI в доках FireCrawl) | меньше галлюцинаций, чем «по памяти» модели |
| Наблюдаемость | Журнал запусков (Executions) + таблица ошибок | прод-вебхуки в редакторе не видны |

Для Lane Pilot это значит: узел графа вызывает скрипт-адаптер (`sp.run_script`), а не «умную» ноду; адаптер хранит
только ссылку на секрет в каталоге окружения, никогда сам ключ.

## 2. Выбор режима FireCrawl: дерево решений

```
нужен список страниц конкурента?           → map (+ search внутри map, + limit, узкий раздел на входе)
нужно содержимое 1..N известных URL?       → scrape (по одному) или map→scrape батчами
нужен «весь сайт» без ручного отбора?       → crawl (асинхронно: polling или webhook + пагинация next)
нужна выдача по запросу + тексты лидеров?   → search с scrapeOptions (поиск и скрейп одним вызовом)
структура уже скачанного HTML?             → локальный парсинг CSS-селекторами (0 кредитов, 0 токенов)
```

Правило узкого входа: на `map` подаётся URL раздела (например, блога или категории), а не корень. Корень с фильтром
`search` тянет в выдачу услуги, справку и аксессуары; раздел даёт чистый список. Порядок предпочтения фильтрации:
`search` сервиса → `limit` → дочистка кодом.

### 2.1. Модель стоимости одного прогона

Обозначения: `S` — число скрейпов, `P` — доля страниц, которым нужен скрытый прокси, `Q` — число поисковых
запросов, `k` — результатов на запрос, `M` — вызовов map, `C` — страниц в crawl.

```
credits ≈ S·(1 + 5·P) + Q·2·ceil(k/10) + Q·k·(1 + 5·P)·[scrapeOptions включены] + M·c_map + C·(1 + 5·P)
```

- Скрейп страницы — 1 кредит; режим скрытого прокси добавляет 5 (страница за защитой стоит 6).
- Поиск — 2 кредита за каждые 10 результатов; при включённом `scrapeOptions` каждая найденная страница дополнительно
  оплачивается как скрейп (вывод из общей логики прайса, `[VERIFY]`).
- `c_map` — стоимость вызова map; в уроках не названа, закладывать 1 кредит на вызов `[VERIFY]`.
- Crawl списывает кредиты за **все** обойдённые страницы, даже если ответ забран не полностью (см. §4.2).

Гейт бюджета для графа: прогон без верхней границы (нет `limit`, нет `maxDiscoveryDepth`) — `over_budget`, не запускать.

### 2.2. Экономия до LLM

| Приём | Эффект (по демонстрации в уроках) | Когда не помогает |
|---|---|---|
| `includeTags` / `excludeTags` по CSS-селекторам | каталог: ~700 слов → ~500, ~7,5 тыс. → ~4,2 тыс. символов | селекторы меняются при редизайне — нужен тест |
| `onlyMainContent: true` | на каталогах эффекта не дал | надёжен только на статьях; проверять на своём типе страниц |
| `ignoreQueryParameters: true` в map | убирает UTM-дубли из списка | — |
| `formats: json` по схеме с `required` | одна запись на страницу, без лишнего текста | сложные вложенные страницы — массив объектов |
| Локальный HTML-парсер | H1–H4, `href`, `src`, мета без трат кредитов на extract | контент рендерится только JS — нужен формат `html` с ожиданием |

Схема JSON-извлечения: поля, без которых запись бессмысленна (название, цена), — в `required`. Тогда пустое значение
приходит как `null`, ключ сохраняется и цепочка не падает; без `required` извлечение рвётся на первой странице без поля.

## 3. Пропускная способность: батчи и паузы

Ограничение на практике — частота запросов, а не кредиты: 10 запросов в минуту на бесплатном тарифе, 100 — на
младшем платном. Для цикла «батч размера `B` → пауза `W` секунд» при среднем времени скрейпа `t`:

```
B · 60 / (W + t) ≤ R      ⇒      W ≥ 60·B / R − t
```

Пример: `R = 10`, `B = 3`, `t ≈ 3 с` → `W ≥ 15 с` — ровно та пауза, на которой стабилизировался учебный конвейер
(207 товаров из 16 подкатегорий без ошибок rate limit). На платном тарифе (`R = 100`) та же пачка требует `W ≈ 0`.

Правила цикла:
1. Число итераций цикла ≠ числу страниц: считать прогресс по строкам результата.
2. При отладке закреплять (pin) выход предыдущих узлов; перед боевым запуском открепить.
3. Перед перезаписью таблицы — явная очистка или upsert по ключу URL, иначе строки дублируются.

## 4. Асинхронный crawl

### 4.1. Polling против webhook

| Схема | Цепочка | Цена | Когда |
|---|---|---|---|
| Polling | POST `/v2/crawl` → пауза 5 с → GET `/v2/crawl/{id}` → проверка `status == completed` → повтор | держит воркер занятым; 10–20 параллельных циклов ощутимо грузят n8n | разовые прогоны, < 50 страниц |
| Webhook | Отправитель: POST с объектом `webhook {url, events: [completed, failed]}`; Получатель: триггер-вебхук → GET по `id` | воркер свободен | расписание, много параллельных задач |

Вебхук несёт **сигнал**, а не данные: тело события — тип (`crawl.completed`) и `id`; результат забирается отдельным GET.
Тестовый URL вебхука слушает не дольше 120 секунд — тестовый прогон должен укладываться (например, 5 страниц по 8 с).

### 4.2. Пагинация ответа

Crawl на 500 страниц списал 500 кредитов, а первый GET вернул 100 записей: остальное лежит по ссылке `next`.
В HTTP-узле получения результата включается пагинация «следующий URL из ответа», остановка — пустой `next`,
страховочный максимум страниц обязателен. Потолок одного ответа n8n — порядка 10 МБ; при большем объёме дробить
по `includePaths` или писать порции во внешнее хранилище.

### 4.3. Безопасность продового вебхука

Production-URL открыт всему интернету. Без проверки подписи любой может запустить workflow, а если внутри есть LLM
или платный API — потратить бюджет. Минимальный контракт:

1. Включить получение «сырого» тела запроса.
2. Пересчитать HMAC от тела с секретом подписи (FireCrawl: Settings → Advanced) и сравнить с заголовком подписи.
3. Ветка «подпись не сошлась» → запись в таблицу отказов, без дальнейших вызовов.
4. Секрет — только в credential/переменной окружения сервера n8n; в коде узла — ссылка на переменную.

## 5. Мониторинг конкурентов (Change Detection)

В курсе мониторинг построен как **собственный дифф через таблицу**, а не через встроенный формат отслеживания
изменений FireCrawl. Это осознанный выбор: таблица — одновременно состояние, журнал и интерфейс для человека.

### 5.1. Схема данных

| Поле | Тип | Назначение |
|---|---|---|
| `url` | string, ключ | страница конкурента |
| `entity` | string | товар / услуга / страница |
| `watched_field` | enum: `price`, `title`, `h1`, `offer`, `content_hash` | что сравниваем |
| `last_value` | string/number | значение прошлой проверки |
| `last_checked_at` | ISO date | дата прошлой проверки |
| `change_count_30d` | int | счётчик изменений (расширение) |

### 5.2. Алгоритм прогона

```
по расписанию (день/неделя):
  rows ← таблица наблюдения
  для каждой пачки из B строк:
    current ← scrape(url, formats=json, schema={watched_field}, required=[watched_field])
    пауза W (см. §3)
    если current is null           → статус «не извлечено», не алерт (иначе ложные тревоги при редизайне)
    иначе если norm(current) ≠ norm(last_value):
        алерт в мессенджер: сущность, было → стало, ссылка
        upsert строки по url: last_value=current, last_checked_at=now, change_count_30d += 1
    иначе: обновить только last_checked_at
```

Нормализация (`norm`) обязательна: пробелы, валюта, разделители разрядов, регистр. Для текстовых полей — хэш
очищенного Markdown основного блока (после `includeTags`), иначе меняющиеся баннеры и даты дают шум.

### 5.3. Бюджет мониторинга

```
кредиты/мес = URL_под_наблюдением × запусков_в_месяц × (1 + 5·P)
```

200 URL ежедневно ≈ 6 000 кредитов в месяц без прокси. Отсюда правило частоты: цены и офферы — ежедневно, контент
и структура — еженедельно, архивные страницы — ежемесячно.

### 5.4. Расширения для графа (не из курса, предложение)

- Встроенный режим отслеживания изменений FireCrawl как второй источник, когда нужен построчный дифф текста `[VERIFY]`.
- Дебаунс: алерт только если изменение подтвердилось двумя прогонами подряд или затронуло ≥ 2 полей.
- Сводка вместо потока: одно сообщение на прогон, длинные тексты резать по 4 000 символов (лимит мессенджера).

## 6. Выгрузка Search Console через API

### 6.1. Подключение (чек-лист отказов)

1. Проект в Google Cloud под тем же аккаунтом, где подтверждены сайты; включить Search Console API.
2. OAuth client типа Web application; redirect URI — ровно тот, что показывает n8n (у self-host — свой домен).
3. В разделе аудитории добавить свою почту в тестовые пользователи (публиковать приложение не нужно).
4. Scope не пустой: `https://www.googleapis.com/auth/webmasters` (для чтения достаточно `.readonly` — решение проекта).
5. `siteUrl` — буква в букву как ресурс в GSC (`https://site.ru/` или `sc-domain:site.ru`), URL-кодированный.

### 6.2. Контракт запроса `searchAnalytics.query`

| Параметр | Значение по умолчанию в конвейере | Комментарий |
|---|---|---|
| `startDate` = `endDate` | сегодня − 4 дня | данные стабилизируются 3–4 дня; один день на запрос |
| `dimensions` | `query`, `page` | также `country`, `device`, `date` |
| `type` | `web` | `image`, `video`, `news` — отдельными запросами |
| `rowLimit` | 25 000 | максимум на запрос |
| `startRow` | 0, затем +25 000 | если вернулось ровно 25 000 строк — запросить следующую страницу |
| `dimensionFilterGroups` | исключение бренда: `excludingRegex` с `(?i)бренд\|brand` | операторы: equals, notEquals, contains, notContains, includingRegex, excludingRegex |
| `aggregationType` | `byPage` для анализа каннибализации, по ресурсу — для сводок | по ресурсу две страницы сайта в выдаче считаются одной |

Метрики не выбираются: всегда приходят клики, показы, CTR и позиция. Практический потолок — около 50 тыс. строк на
сочетание «ресурс × день × тип»; для большинства сайтов хватает.

### 6.3. Типовые отчёты

| Отчёт | dimensions | Фильтр | Узел-потребитель |
|---|---|---|---|
| Небрендовые запросы за день | query, page | excludingRegex бренда | `seo-monitor` |
| Каннибализация | query, page; `byPage` | ≥ 2 URL на запрос с показами | `seo-structure-audit` |
| Устройства / страны | query, device / country | — | `seo-drop-diagnosis` |
| Ряд по дням | date, page | regex раздела | `seo-measurement-loop` |

## 7. FireCrawl как инструмент агента

- Инструмент — код-обёртка с одним действием (`browse_page`): берёт URL из аргументов модели, проверяет его, вызывает
  `/v2/scrape` (`markdown`, `onlyMainContent`, ожидание загрузки), обрезает ответ (около 60 тыс. символов) и
  возвращает ошибку текстом, чтобы агент понимал причину.
- Описание инструмента — коротко и по-английски.
- Не больше трёх инструментов на агента: дальше качество выбора инструмента падает.

## 8. Сквозной конвейер «запрос → лидер → стратегия»

```
запрос ─▶ search(limit=1..10, scrapeOptions=markdown) ─▶ домен лидера
       ─▶ map(домен, limit≈150) ─▶ фильтр URL блога (код) ─▶ scrape последних 5 статей
       ─▶ выбор репрезентативной статьи ─▶ LLM «SEO-стратег» ─▶ отчёт (порции по 4 000 символов)
```

Генерация такого workflow встроенным билдером даёт скелет, не решение: заранее написать техзадание-промпт, ждать
2–3 итерации отладки.

## 9. Self-host n8n (минимум)

Ubuntu 24.04; сервер вне РФ (часть LLM-API блокирует российские IP); полный стек (n8n, Postgres, мониторинг, Redis,
reverse proxy с автоматическим TLS) — от 4 vCPU / 20 ГБ RAM / 60 ГБ диска, базовая установка — меньше; домен с
wildcard-поддоменами и A-записями на IP; страницу итогов установки с учётными данными сохранить сразу (перенести в
менеджер секретов); активировать бесплатную Community-лицензию; воркеры n8n — 2–5 при параллельных процессах.

## 10. Привязка к графам Lane Pilot (метка `seo-competitor-serp`)

| Узел / граф | Что берёт из этого справочника | Гейт |
|---|---|---|
| `seo-monitor` (недельный тик) | §5 мониторинг конкурентов, §6 небрендовые запросы | бюджет кредитов §5.3 ≤ месячного лимита проекта |
| `seo-research` (SERP-конкуренты) | §2 map/search, §8 конвейер лидера | `limit` и глубина заданы; лимит частоты §3 |
| `seo-tech-audit` | метаданные ответа scrape (статус, robots, canonical, og, CMS) | только чтение |
| `seo-structure-audit` | §6.3 каннибализация `byPage` | ≥ 2 URL на запрос → кандидат |

Детерминированные пороги для узлов:

| Гейт | Правило | Провал → |
|---|---|---|
| FC-1 бюджет | прогноз кредитов по §2.1 ≤ дневного лимита; нет прогона без `limit` | `over_budget` |
| FC-2 частота | `W ≥ 60·B/R − t` для тарифа проекта | уменьшить `B` |
| FC-3 вебхук | подпись проверяется до первого платного вызова | `blocked_insecure` |
| FC-4 null-значение | извлечённое поле `null` не считается изменением | `not_extracted`, без алерта |
| GSC-1 окно | `endDate ≤ today − 3` | сдвинуть окно |
| GSC-2 пагинация | ровно 25 000 строк → запрос `startRow + 25000` | неполная выгрузка |
