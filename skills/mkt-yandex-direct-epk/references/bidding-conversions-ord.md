# Яндекс Директ ЕПК: Конверсионные стратегии, кросс-минусация, ОРД и управление бюджетом

> **Целевой скилл**: `mkt-yandex-direct-epk`
> **Назначение**: Инженерный регламент настройки автостратегий и `PriorityGoals` в API v501, выбора микро- и макроконверсий по порогу обучающей выборки, операторов соответствия и кросс-минусации, соблюдения требований маркировки рекламы (ОРД / `erid`), контроля открутки (budget pacing) и защитных шлюзов живых мутаций.

## 1. Микро- vs Макроконверсии и математика обучения автостратегий

Алгоритмы конверсионного аукциона Яндекс Директа (`WB_MAXIMUM_CONVERSION_RATE`, `AVERAGE_CPA`, `PAY_FOR_CONVERSION`, `AVERAGE_CRR`, `PAY_FOR_CONVERSION_CRR`) требуют стабильного потока целевых событий на уровне **конкретной кампании**:

$$\text{Порог устойчивого обучения} \ge 10\text{–}15 \text{ конверсий в неделю на 1 кампанию}$$

Если кампания приносит `2–4` продажи в неделю, обучение распадается: стратегия либо зажимает охваты до нуля (особенно на `PAY_FOR_CONVERSION`), либо хаотично завышает ставки в попытке нащупать аудиторию.

### Лестница выбора цели оптимизации

| Объём макроконверсий (оплат / квал. лидов) в неделю | Выбор цели оптимизации | Схема настройки `PriorityGoals` |
|---|---|---|
| **`>= 15` оплат / квал. сделок CRM** (передаются офлайн-конверсиями в Метрику) | Чистая макроконверсия (`qualified_lead` / `paid_order`) | Единственная цель в стратегии, ценность = маржинальная прибыль сделки |
| **`10..14` заявок с сайта (`lead_submit`)**, но `< 10` оплат | Отправка валидированной формы / целевой звонок коллтрекинга (`>= 30–45 сек`, уникальный) | Макроцель `paid_order` (вес 100%) + цель `lead_submit` (вес = $\text{CR}_{\text{lead}\to\text{sale}} \times \text{Margin}$) |
| **`< 10` заявок на старте / узкий B2B** | Квалифицированная микроконверсия с высокой корреляцией с покупкой (расчёт в калькуляторе, переход в мессенджер с кодом заявки, открытие 3-го шага квиза) | Лестница `PriorityGoals` с взвешиванием по воронке; **запрещено** оптимизироваться на «мусорные» микроцели («провёл на сайте 60 сек», «проскроллил 50%», «кликнул по любому элементу»), так как автостратегия (особенно в РСЯ) мгновенно выкупает ботный и развлекательный трафик |

### Расчёт экономической ценности микроцели для `PriorityGoals`
Пусть маржа с продажи $M = 20\,000\text{ ₽}$, конверсия из заявки в продажу $\text{CR}_2 = 20\%$, конверсия из расчёта калькулятора в заявку $\text{CR}_1 = 15\%$. Тогда математически согласованные ценности целей в ЕПК:
- `paid_order` (офлайн-конверсия из CRM): $V_3 = 20\,000\text{ ₽}$
- `lead_submit` (отправка формы / целевой звонок): $V_2 = 20\,000 \times 0.20 = 4\,000\text{ ₽}$
- `calc_complete` (финал калькулятора): $V_1 = 4\,000 \times 0.15 = 600\text{ ₽}$

> **Нюанс API v501 для `PriorityGoals`**:
> - При **создании** кампании (`Campaigns.add`) массив `PriorityGoals.Items` передаётся **без поля `Operation`**.
> - При **обновлении** кампании (`Campaigns.update`) объект `PriorityGoals` **обязан** содержать `"Operation": "SET"` (иначе API отклоняет запрос).

## 2. Матрица стратегий ЕПК и ловушки микро-валюты (`micros`)

### 2.1. Специфика стратегий в `UNIFIED_CAMPAIGN` (API v501)
1. **Нет `AVERAGE_ROI`**: в отличие от классических кампаний, в ЕПК стратегия `AVERAGE_ROI` отсутствует — вместо неё используются стратегии доли рекламных расходов **`AVERAGE_CRR`** (средняя ДРР) и **`PAY_FOR_CONVERSION_CRR`** (оплата за конверсии по целевой ДРР), требующие передачи электронной коммерции (`dataLayer` -> Метрика) или ценности цели.
2. **Конфликт `DailyBudget` и автостратегий (ошибка `6000`)**: поле `DailyBudget` на уровне кампании допустимо **только** на ручных стратегиях (`HIGHEST_POSITION`). Указание `DailyBudget` при любой автостратегии (`WB_*`, `AVERAGE_*`, `PAY_FOR_CONVERSION*`) вызывает ошибку `6000` (`Inconsistent object state`). В автостратегиях потолок расхода задаётся исключительно через `WeeklySpendLimit`.
3. **Защита `PAY_FOR_CONVERSION` от финансового пробоя**:
   - Неснижаемый остаток на счёте кабинета обязан составлять минимум `3 × TargetCPA` (рекомендуемо `5–10 × TargetCPA` или проектный недельный бюджет), иначе открутка замирает.
   - При смене настроек стратегии внутри недели счётчик `WeeklySpendLimit` может перезапуститься — резкие правки в середине недели способны привести к перерасходу относительно исходного недельного плана.
   - Период обучения автостратегии составляет `7–14` дней; запрещено менять целевой `CPA` / `WeeklySpendLimit` более чем на `15–20%` за один шаг и чаще одного раза в 3–5 дней.

### 2.2. Микро-валюта (`× 1 000 000`)
Все денежные поля API Директа (`WeeklySpendLimit`, `BidCeiling`, `AverageCpa`, `Cpa`, `AverageCpc`, `SearchBid`, `Cost` в Reports API с `Format: TSV` без `returnMoneyInMicros: false`) передаются в целых микро-единицах валюты аккаунта (`int64`):

$$\text{Amount}_{\text{API}} = \text{round}(\text{Amount}_{\text{currency}} \times 1\,000\,000)$$

Ошибка на `10^6` при прямой передаче рублей превращает ставку `150 ₽` в `0.00015 ₽` (нулевой показ) или дневной бюджет в миллиарды микро-единиц. Перед любой записью проверяется валюта клиента через `Dictionaries.get{"DictionaryNames": ["Currencies"]}` (`RUB`, `BYN`, `KZT`, `EUR`, `USD`), так как минимальный недельный бюджет и минимальный шаг ставки зависят от валюты кабинета.

### 2.3. Ограничения корректировок ставок (`BidModifiers`) в ЕПК
В ЕПК API v501 поддерживаются **только 4 типа корректировок**:
- `MobileAdjustment`
- `DesktopAdjustment`
- `DesktopOnlyAdjustment`
- `VideoAdjustment`

Попытка передать через API для ЕПК демографические (`DemographicsAdjustment`), региональные (`RegionalAdjustment`) или ретаргетинговые (`RetargetingAdjustment`) корректировки завершается **ошибкой `8000`**. Ограничение частоты показов (`Frequency Capping`) в ЕПК настраивается только через веб-интерфейс. Значение `BidModifier` задаётся в процентах от базовой ставки: `100` = без изменений (`0%`), `0` = полное отключение устройства (`-100%`), `150` = `+50%`.

## 3. Операторы соответствия, минусация и кросс-минусация

### 3.1. Справочник операторов ключевых фраз Яндекс Директа

| Оператор | Синтаксис | Действие | Где применять | Где опасно применять |
|---|---|---|---|---|
| Без операторов | `ремонт турбин москва` | Любые словоформы, порядок слов, плюс дополнительные слова внутри запроса | Базовый сбор семантики с активным списком минус-слов | Однословные ВЧ-фразы (`турбина`) — притянут инфо-трафик |
| Точная словоформа `!` | `купить !билеты !в сочи` | Фиксирует падеж, число и время слова | Омонимы в разных падежах (`!лечение кариеса` vs `лечению`), модели и артикулы | Переспам `!` отрезает естественные падежные формулировки |
| Фиксация стоп-слова `+` | `работа +на дому`, `тур +в турцию` | Принудительно учитывает предлоги, союзы, местоимения | Различение смысла предлога (`кредит +без справки`, `доставка +из китая`) | Лишние `+и`, `+для` без смысловой нагрузки |
| Точное количество слов `"..."` | `"ремонт турбин цена"` | Показы только по этим словам и их словоформам без любых добавочных слов | Отсечение информационного хвоста у ВЧ-маркеров (`"ремонт турбин"` без `видео`, `своими руками`) | Узкие НЧ-фразы — обрушит охват до статуса «Мало показов» |
| Фиксированный порядок `[...]` | `[билеты москва казань]` | Сохраняет строгую последовательность слов (словоформы разрешены, слова между скобками не вставляются) | Маршруты транспорта, направления обмена валют (`[обмен рубль юань]`), B2B «кто кому» | Обычные товарные запросы (`[купить диван угловой]` отсечёт `угловой диван купить`) |
| Группировка `(a\|b)` | `ремонт (турбин\|акпп) москва` | Компактная запись альтернатив в пределах лимита 7 слов | Объединение близких микро-НЧ против статуса «Мало показов» | Смешивание разных посадочных и цен в одной фразе |

### 3.2. Трёхуровневая архитектура минус-слов и кросс-минусация
1. **Единые наборы (`NegativeKeywordSharedSets`) + уровень кампании (`Campaign.NegativeKeywords`, до 20 000 симв.)**: универсальный нецелевой интент (`бесплатно`, `скачать`, `торрент`, `реферат`, `курсовая`, `вакансии`, `зарплата`, `отзывы сотрудников`, `своими руками`, `авито`, `бу`, `инструкция`, `схема`, `форум`).
2. **Уровень группы (`AdGroup.NegativeKeywords`, до 4 096 симв.)**: локальные отсечения для конкретного кластера.
3. **Кросс-минусация между группами/ключами**: если в кампании одновременно живут широкая фраза `ремонт турбин` (Группа А, общий лендинг) и узкая фраза `ремонт турбин дизельных` (Группа Б, специализированный лендинг с дизельным прайсом), без кросс-минусации запрос пользователя «ремонт дизельных турбин» может выиграть Группа А с более общим объявлением. В Группу А добавляется минус-слово `-дизельных`.
   - *Правило анти-самоблокировки*: при добавлении минус-слова с оператором `!` или без него всегда проверять, не минусует ли оно целевую фразу внутри самой группы; в РСЯ минусация на уровне групп **запрещена**, так как минусует не запрос, а весь текстовый контент веб-страницы площадки.

### 3.3. Регулярная чистка через `SEARCH_QUERY_PERFORMANCE_REPORT`
Еженедельно (а в первые 7 дней после запуска — каждые 48 часов) запрашивается отчёт реальных поисковых запросов (`yandex_direct_get_search_terms` / Reports API):
- Запросы с расходом `> 1.5 × TargetCPA` и `Conversions == 0` при нерелевантном интенте — вычленяются корни мусорных слов и добавляются через `yandex_direct_negative_keywords_add`.
- Конверсионные запросы из `---autotargeting` (`CriteriaType == "AUTOTARGETING"`), дающие лиды дешевле целевого CPA, переносятся в явное семантическое ядро отдельной релевантной группой с точным заголовком.

## 4. Маркировка рекламы в РФ (ФЗ-38 / ЕРИР / ОРД и токен `erid`)

Любое размещение интернет-рекламы на аудиторию РФ обязано проходить регистрацию в **Едином реестре интернет-рекламы (ЕРИР)** через оператора рекламных данных (**ОРД Яндекса** для Яндекс Директа).

### Обязательный чек-лист комплаенса ОРД перед запуском кампании
1. **Заполнение реквизитов конечного рекламодателя в кабинете Директа** до отправки первого объявления на модерацию:
   - ИНН, ОГРН / ОГРНИП, организационно-правовая форма (`ООО`, `ИП`, физлицо), полное наименование;
   - При работе через агентство / посредника: полная цепочка договоров (`Рекламодатель -> Посредник -> Площадка`) с номерами, датами, предметом договора и признаком участия в расчётах.
2. **Автоматическая выдача `erid`**: при корректно заполненном блоке «Данные рекламодателя» ОРД Яндекса автоматически присваивает каждому креативу ЕПК уникальный токен `erid`, добавляет плашку «Реклама • ООО …» в объявление и дописывает параметр `?erid=...` при клике.
3. **Защита посадочной от поломки `?erid=` и `yclid=`**:
   - Сервер посадочной страницы **не должен** делать `301/302` редирект с отрезанием незнакомых query-параметров (`erid`, `yclid`, `utm_*`) и не должен отдавать `404/500` из-за строгого белого списка GET-параметров в WAF/роутере.
   - В Яндекс Метрике («Операции» счётчика) и канонических URL рекомендуется исключать `erid` и `yclid` из склейки URL отчётов страниц входа, чтобы один лендинг не дробился на тысячи уникальных строк в отчёте «Страницы входа».
4. **Ежемесячное закрытие актов в ОРД (до 30 календарных дней после окончания отчётного месяца)**: сверка разаллокации актов по изначальному договору рекламодателя при агентской схеме оплаты; за отсутствие маркировки или недостоверные сведения по ст. 14.3 ч. 15–17 КоАП РФ предусмотрены оборотные/фиксированные штрафы до 500 000 ₽ на юрлицо за каждый факт нарушения.

## 5. Pacing бюджета, мониторинг выгорания и защитные шлюзы `ohmy-seo`

### 5.1. Контроль темпа расхода (Budget Pacing)
Пусть месячный бюджет канала $B_{\text{month}}$, прошло $d$ дней из $D$ календарных дней месяца, фактический накопленный расход с НДС равен $S_{\text{actual}}$:

$$\text{ExpectedSpend}(d) = B_{\text{month}} \times \frac{d}{D}, \qquad \text{PacingRatio} = \frac{S_{\text{actual}}}{\text{ExpectedSpend}(d)}$$

- **`PacingRatio` в коридоре `[0.90, 1.10]`**: штатный темп открутки.
- **`PacingRatio > 1.15` (перекрут)** или сгорание дневного лимита до `14:00` по часовому поясу региона: аукцион перегрет; на ручной стратегии снижаются ставки / `BidCeiling`, на автостратегии плавно (`-15%`) корректируется `WeeklySpendLimit` или ужесточается `AverageCpa` (без резких скачков `>20%`).
- **`PacingRatio < 0.75` (недокрут)**: проверить баланс кабинета (`StatusPayment == ALLOWED`, остаток `>= 3 × CPA`), долю отклонений модерации (`Status == REJECTED`), статус «Мало показов» у групп, зажатый `BidCeiling` или слишком низкий `TargetCPA` ниже рыночного уровня аукциона (`AuctionBids`).
- **Учёт НДС (20%)**: API отчётов Директа по умолчанию возвращает расходы без НДС или с НДС в зависимости от параметра `IncludeVAT: "YES" | "NO"`. В сквозной аналитике и сверке с финансовым P&L всегда явно фиксировать `IncludeVAT: "YES"` (или единый стандарт проекта в `project-dossier.json`).

### 5.2. Защитные гейты живых мутаций в `mcp-yandex-seo`
Инструменты записи в `ohmy-seo` защищены многоуровневым предохранителем от случайного слива рекламного бюджета агентом:
1. Переменные окружения хоста: `OHMY_SEO_ALLOW_LIVE_MUTATIONS=true` и `YANDEX_DIRECT_ALLOW_LIVE_MUTATIONS=true`.
2. Аргументы вызова инструмента: `confirm: true` и явный флаг подтверждения живого аккаунта `acknowledge_live`.
3. Любое массовое изменение ставок (`> 50` фраз или дельта `> 100%`), перераспределение недельных бюджетов `> 20%` или остановка конверсионных кампаний сначала просчитывается как дифф (текущее значение -> новое значение -> расчётное изменение расхода ₽/день) и применяется атомарно с записью `RequestId` в журнал операций.
