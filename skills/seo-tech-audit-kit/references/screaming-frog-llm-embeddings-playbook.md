# Screaming Frog: краул больших сайтов, Custom-инструменты, LLM-колонки и эмбеддинги

> [!NOTE]
> Синтез собственными словами по курсу Q1 2026 (Максим Котёнков). Названия пунктов меню — как в интерфейсе SF 23.x.
> Пороги, отмеченные `[эмпир.]`, взяты из демонстраций и требуют калибровки на своём сайте.

## 1. Модель краула: что стоит ресурсов

Краулер работает циклом «очередь → HTTP-запрос → разбор HTML (при 200) → новые URL в очередь с дедупликацией».
Расход памяти и диска определяется не числом URL, а **числом сохранённых связей**:

```
объём_связей ≈ URL × средн_ссылок_на_страницу        (~100 ссылок на страницу — типичный шаблон)
диск_БД ≈ 66 КБ × URL   [эмпир.: 15 ГБ на ~228 тыс. URL → 1–2 млн URL = 45–90 ГБ]
```

Каждый тип ресурса имеет два независимых флага:

| Crawl | Store | Что получаем | Когда |
|---|---|---|---|
| да | да | статусы + все связи inlinks/outlinks | по умолчанию, аудиты до десятков тысяч URL |
| да | нет | статусы и базовые поля, без «откуда ссылка» | экономия памяти; поиск 404 без источников |
| нет | да | фиксируем встреченное, но не идём дальше | пагинация rel next/prev, hreflang-атрибуты |
| нет | нет | полный игнор | тип не нужен задаче |

Компромисс: выключив Store у CSS/JS/внешних ссылок, вы увидите битый ресурс, но не страницу-источник. Для
шаблонных сайтов это приемлемо: битую ссылку из шаблона находят по шаблону. Для JS-рендера Crawl у JS/CSS/Images
обязателен — иначе рендер получится «голым».

## 2. Протокол большого сайта (> 100 тыс. URL)

### 2.1. Сначала не краулить

Порядок, при котором полный краул часто оказывается не нужен:

1. **Цель аудита** сформулирована одной строкой (битые ссылки? индексация? дубли? перелинковка?).
2. **GSC и Вебмастер** — источник «видимых» URL и уже известных проблем. Страницы с показами выгружаются
   (25 тыс. строк на запрос, дробить фильтрами по разделам) и подаются в **List mode**. Пример из курса: из миллионов
   URL ~22 тыс. страниц с трафиком дали полноценный аудит.
3. **Разведочный краул**: 1 час или лимит 10–50 тыс. URL. Задача — найти «взрыватели» объёма: пагинация,
   сортировки, фильтры, метки, внутренний поиск, неожиданные картинки, 5xx/429.
4. **Глубокий аудит части**: 500–1000 страниц на каждый тип шаблона (у типичного крупного сайта ~20 типов).
5. Только затем — решение о полном краул; если да, то Database + SSD, порциями, при необходимости облачная машина.

Обоснование: проблемы шаблонного сайта повторяются; после первых сотен страниц типа новая информация почти не
появляется. «Миллион дублей» из-за открытой пагинации — **одна** задача разработчику, а не выгрузка на миллион строк.

### 2.2. Память и хранилище

| Параметр | Правило |
|---|---|
| Storage Mode | Database на SSD для всего, что не помещается в RAM; ориентир гайда — 16 ГБ RAM ≈ 500 тыс. URL (считать все ресурсы) |
| Memory Allocation | от 4 ГБ, до ~1/3 RAM, минимум 2–3 ГБ оставить ОС (16 ГБ → до 8 ГБ, 32 ГБ → 16 ГБ) |
| Малые сайты | Memory быстрее (анализ в RAM) |
| HDD | перенести папку БД на SSD (подходит и внешний) |

### 2.3. Скорость

```
фактическая_частота = min(Max Threads × 1/t_ответа, Limit URL/s)
время_краула ≈ URL / фактическая_частота          (1 млн URL при 5 URL/s ≈ 2,3 суток)
```

- Max Threads по умолчанию 5; поднимать ступенями (5 → 10 → 15) с 5–10-минутным наблюдением за 5xx/429 и
  собственным CPU/RAM.
- Потоки и URL/s согласуются с разработчиком: whitelist IP, ночное окно, учёт других ботов.
- Нестабильный сервер: 1–3 повтора на 5xx; не включать, если сервер банит повторы. Response Timeout 20 с по
  умолчанию — увеличивать для медленных бэкендов.

### 2.4. Limits: квоты вместо полного обхода

| Лимит | Назначение | Стартовое значение |
|---|---|---|
| Limit Crawl Total | общий потолок | 200–2 000 при отладке, 10–50 тыс. разведка |
| Limit Crawl Depth | глубина от стартовой точки | 3–5 для верхних уровней |
| Limit URLs Per Crawl Depth | репрезентативная выборка по уровням, защита от «взрыва» на глубине | 500–15 000 на уровень |
| Limit Max Folder Depth | глубина по папкам URL; спасает на бесструктурных URL | ~5 |
| Limit Number of Query Strings | 0 — без параметров; 1 — только первый параметр (фильтр-страницы) | 0–2 |
| Limit Crawl Total Per Subdomain | квота на поддомен при обходе всех поддоменов | ~1 000 на поддомен для оценки |
| Max Redirects to Follow | цепочки редиректов | 10 по умолчанию; нормальная цепочка — 2–3 шага |
| Max URL Length to Crawl | ловушка Bitrix/фильтров с накоплением параметров | реальный максимум нормальных URL + запас (обычно 200–500) |
| Limit by URL Path | квоты разделам: `/catalog/` 10 000, `/blog/` 500, `/help/` 300 | «паутина» сайта без полного обхода |

Два готовых профиля:

- **Быстрый срез**: Total 50 000; Depth 5; Query Strings 2; Max Links per URL 200.
- **Фасетный каталог**: Query Strings 1–2; Max URL Length 300–500; Limit by URL Path на `/catalog/`, `/filter/`, `/search/`.
- **Глубокий аудит части**: Total 20–30 тыс.; Depth 3; ~15 тыс. на уровень; Folder Depth 5; Query Strings 0.

### 2.5. Include / Exclude / Rewrite / robots

| Механизм | Что делает со связями | Когда |
|---|---|---|
| Include (regex) | обходит только совпавшие URL; без якоря `^` ловит подстроку где угодно | раздел целиком |
| Exclude (regex) | URL не обходится → страницы, доступные только через него, пропадают | мусорные параметры, UTM, `page=` |
| URL Rewriting | URL переписывается и обходится в каноническом виде → связи сохраняются | трекинг-параметры во внутренних ссылках, http→https |
| robots.txt (Respect + скрыть заблокированные) | чистый обход по правилам сайта | robots уже закрывает мусор |
| Custom robots.txt | песочница для проверки нового файла до выкладки | релиз robots.txt |

Шаблоны регулярных выражений (подставить свой домен):

```
только раздел:            ^https?://(www\.)?site\.ru/blog/.*
несколько разделов:       ^https?://(www\.)?site\.ru/(blog|news|articles)/.*
только первый уровень:    ^https?://(www\.)?site\.ru/[^/]+/?$
любые параметры:          \?
UTM-метки:                [?&]utm_
пагинация:                [?&]page=\d+
```

Respect Noindex / Canonicals / Next-Prev **не запрещают обход**, а прячут страницы из отчётов (исходящие ссылки
учитываются). Для регулярного мониторинга — включать; для первого глубокого аудита — выключать, иначе не видно
проблем на noindex-страницах.

## 3. Рендеринг JavaScript: доказать необходимость

Дерево решения:

```
есть пререндер/SSR для ботов?  ── да ─▶ UA = Googlebot Smartphone, рендер выключен; сверить с разработчиком
            │ нет / неизвестно
            ▼
выборка: по 1–3 URL каждого шаблона в List mode с рендером, Store HTML + Store Rendered HTML
            ▼
вкладка JavaScript: доля контента/ссылок/мета, которые есть только после JS
            ▼
доля > ~10 % контента или меняются title/canonical/robots/hreflang/ссылки  ── да ─▶ рендер нужен для этого шаблона
            │ нет
            ▼
краул без рендера
```

Параметры рендера: AJAX Timeout 5 с по умолчанию → 10–15 с для медленных фронтендов; окно Googlebot Smartphone;
«Resize to Content» для полноэкранного скриншота (до 8 192 px). После краула проверить вкладку Blocked Resources:
JS/CSS, закрытые в robots.txt, ломают рендер. Сравнение raw vs rendered — View Source → Show Difference.
Расхождение мобайл/десктоп без разработчика: краул пары страниц двумя UA и сравнение колонки Hash.

## 4. Custom-инструменты: лестница сложности

| Уровень | Инструмент | Отдаёт | Типичные задачи | Требует |
|---|---|---|---|---|
| 1 | Custom Search | факт и счётчик (contains / does not contain; text / regex) | забытые счётчики, lorem ipsum, «0 руб.», старый бренд, теги noindex для Яндекса | зону поиска |
| 2 | Custom Extraction | значение в колонку (XPath / CSS / Regex; Inner HTML, HTML element, Text, Attribute, Function Value) | цены, телефоны, характеристики, JSON-LD, сверка цены в разметке и на странице | до 100 колонок |
| 3 | Custom JavaScript | действие (Action) или значение (Extraction), в т.ч. вызов внешних API | закрыть баннер, проскроллить, SERP-конкуренты, FAQ из выдачи | JS-рендер |
| — | Custom Link Position | позиция ссылки (header/nav/content) | анализ контентной перелинковки | — |

Зоны Custom Search: HTML (серверный), Page Text (видимый текст без анкоров), HTML Head, HTML Body, XPath-блок,
Content Area. Пример ловушки: слово встречается в меню и тегах, но не в абзацах — поиск по Content Area (`p`) честно
возвращает ноль.

Правила для Custom JavaScript:

- Результат отдаётся специальным методом передачи данных SF (строка — одна колонка, массив — несколько); простой
  `return` значения не работает. Асинхронный код оборачивается в немедленно вызываемую async-функцию.
- Порядок исполнения: сначала Action-сниппеты, потом Extraction; каждый сниппет замедляет краул.
- Action имеет тайм-аут по умолчанию 6 с.
- Справку SF по Custom JS отдавать LLM вместе с задачей: без неё модель пишет код, не совместимый с SF.
- Отладка: вывод консоли в окне теста + живой ответ API → обратно в модель на исправление.

## 5. LLM внутри краула

### 5.1. Ограничение «одна колонка — один промпт»

Каждый промпт возвращает одну ячейку. Если нужно несколько полей (например, 5 title и 5 description), модель
просят вернуть **одну CSV-строку с разделителем**, а в таблице режут по столбцам. Экономия: один вызов и одна
отправка контента вместо двух.

### 5.2. Что отправлять в модель (порядок экономии токенов)

1. **List mode** по заранее отобранным проблемным URL, а не весь сайт.
2. **Include/Exclude**, чтобы не гнать в LLM разделы, где генерация не нужна.
3. **Content Area** (исключить nav/footer, оставить `article` или нужный класс).
4. **Custom Extraction / Custom JS** — только нужные поля (H1 + характеристики + категория) через подстановки
   в расширенном промпте.
5. Только после этого — выбор модели: mini/nano/Flash для извлечения, ALT, коротких тегов, массовых описаний;
   полноразмерные модели для многоэтапных промптов и аудитов.

Перед массовым запуском — **тест на одном URL**: окно теста показывает итоговый промпт ровно в том виде, в каком он
уйдёт в API. Ручные промпты требуют явного включения подстановки плейсхолдеров, иначе в API уходят литералы.
Сложная разметка промпта (тройные разделители, угловые ограничители) может ломать подстановку SF — безопаснее
простой текст с входными данными в конце.

### 5.3. Каталог применений (из пресетов курса, описание без копирования)

| Применение | Модель в пресете | Вход | Выход | Контроль качества |
|---|---|---|---|---|
| Title + description пачкой | mini | H1, URL, старые теги, текст | CSV: 5 title (50–60 симв.) + 5 description (140–155 симв.) | длину задавать словами, допуск ±5 символов |
| ALT общий / для e-com | mini (vision) | изображение + его URL как подсказка | одна строка ~100 ± 15 символов | URL картинки — только если не противоречит видимому; декоративным — пусто |
| Универсальный парсер конкурентов | mini | весь контент страницы; домены конкурентов в CDNs | JSON: название, описание, характеристики name/value | `null` для пустых полей, строго валидный JSON |
| Описание товара по характеристикам | mini | H1 + блок характеристик + категория (Extraction) | 250–300 слов, 3–5 абзацев, выгоды вместо перечня | единственный источник фактов — блок данных |
| Отзывы | разные профили | H1 + характеристики | короткие или экспертные отзывы | дозировать по спросу; разные профили вместо «рандома» в одном промпте |
| Актуальность статьи | полноразмерная | текст | «Актуально/Неактуально» + ТЗ | метка первой строкой |
| Семантическая вёрстка | полноразмерная | HTML (+ отчёт валидатора) | список ошибок и ТЗ | по одному URL на тип шаблона |
| Аудит «глазами асессора» | полноразмерная | наш текст + тексты топ-3 (через JS) | строка оценки 0–3, риск, план P0/P1/P2 | без конкурентов оценка бессмысленна |
| Пробелы в структуре | mini | наше дерево H1–H6 + деревья конкурентов | какие блоки добавить/убрать и на каком уровне | не переписывать формулировки |
| FAQ из выдачи | mini/полноразм. | вопросы PAA (XML-выдача) + текст страницы | FAQ-блок + JSON-LD FAQPage | валидатор разметки; если вопросов нет — генерация по теме |

### 5.4. Внешние API через Custom JS: схема «конкурентный контент-аудит»

```
краул страницы ─▶ JS: запрос = H1 (иначе title), нормализация, ≤160 символов
               ─▶ поиск в выдаче + скрейп топ-N (свой домен и поддомены исключены)
               ─▶ JS: дерево H1–H6 нашей страницы (нумерация 1 / 1.1 / 1.1.1)
               ─▶ LLM-колонка 1: аудит контента против топа
               ─▶ LLM-колонка 2: пробелы в структуре заголовков
```

Устойчивые параметры: топ-3 конкурента; лимит ~15 тыс. символов на конкурента и ~30 тыс. на колонку
`[эмпир.: топ-30 ≈ 100 тыс. символов валил программу]`; кэш выдачи 2 суток; тайм-ауты поиска 120 с и скрейпа 90 с;
1 повтор с паузой ~0,8 с на 408/429/5xx; пустая строка вместо исключения при ошибке. Зависимости строгие: LLM-колонка
не стартует, пока JS не вернул результат.

### 5.5. FAQ из выдачи (XML-провайдер)

- Запрос формируется из H1; гео/язык/устройство настраиваются один раз.
- Каждая следующая десятка выдачи — отдельный оплачиваемый запрос: брать только первую.
- Если блока «похожие вопросы» в выдаче нет, вызов всё равно оплачен — LLM придумывает вопросы по тексту
  страницы (запасная ветка).
- Порядок отладки сниппета: вручную убедиться, что блок вопросов есть в выдаче → вывод консоли + сырой XML
  в модель → проверить, что модель не «вычистила» ключ из кода.

### 5.6. Где SF не лучший инструмент

Сценарии с ветвлением, промежуточным хранением и повторными попытками на уровне бизнес-логики переносить в
n8n/скрипт: в SF между шагами ничего не «перекладывается», зато для массовых enrichment-колонок по краулу он быстрее.

## 6. Эмбеддинги: смысловые дубли, нерелевантность, перелинковка

### 6.1. Подготовка вектора

- Модель: small (~1 536 измерений) для коротких полей (title, H1), large (~3 072) для длинного текста.
- Векторизуется **только чистая область**: без шапки, меню, футера, облака тегов и блоков «все бренды». Иначе
  шаблон «размазывает» вектор и любая страница кажется релевантной главной теме сайта.
- Длинный текст обрезать (ориентир — первые ~5 000 символов), иначе ошибки API.
- Можно держать несколько векторов (текст и title) в одном краул и переключать в отчётах.
- Старт: вектор title — дёшево, быстро, не требует чистки области.

### 6.2. Метрики

```
cos(a, b) = (a · b) / (‖a‖ · ‖b‖)
центроид   c = (1/N) Σ vᵢ           по индексируемым страницам без исключённых разделов
релевантность страницы i = cos(vᵢ, c)
```

| Отчёт | Правило | Порог |
|---|---|---|
| Смысловые дубли (Semantic Similarity) | пары с `cos ≥ τ_dup` | 1,0 — копии; рабочая зона ~0,95 [эмпир.] |
| Низкая релевантность | `cos(vᵢ, c) < τ_low` | 0,4 по умолчанию; пересчёт без перекраула |
| Ближайшие к центроиду | top-k по `cos(vᵢ, c)` | «страница, описывающая весь сайт» — если она слабая, это сигнал |
| Семантический поиск | top-k страниц к тексту запроса или описанию новой страницы | k расширять, если ответ шумный |

Ловушки центроида: служебные страницы (политика, условия) насыщены словами основной темы и выглядят релевантными
по тексту, но уходят в «низкую релевантность» по title. Сверять оба вектора.

### 6.3. Алгоритм «смысловая каннибализация»

```
1. Только индексируемые страницы; исключить пагинацию, контакты, служебные разделы.
2. Вектор чистой области (или title) для каждой страницы.
3. Пары (i, j) с cos ≥ 0,95 → кандидаты.
4. Для кандидата подтянуть GSC (query × page, aggregationType=byPage):
     общий запрос, по которому обе страницы получают показы → каннибализация подтверждена.
5. Решение по паре: склейка с 301 / разведение интентов / canonical / оставить (разные интенты при общем бренде).
```

Только векторный сигнал недостаточен: «BMW X5» и «BMW X6» близки по смыслу, но это разные посадочные. Без шага 4
решение не принимается.

### 6.4. Алгоритм «доноры перелинковки для новой страницы»

```
1. Сформулировать новую страницу (title + 2–3 предложения) → вектор q.
2. top-k (k = 10–20) ближайших индексируемых страниц по cos(q, vᵢ).
3. Отбросить страницы с > N исходящих контентных ссылок и неиндексируемые.
4. Каждой из 2–5 лучших — контекстная ссылка на новую страницу (анкор из её семантики).
5. Проверить вручную: косинус путает тонкие признаки класса (пример курса: «аренда спорткара» → модель-кроссовер
   с похожим названием).
```

То же ранжирование используется для выбора цели склейки/редиректа при удалении страницы. Встроенная карта
редиректов по эмбеддингам в курсе оценена как слабая — проверять каждую пару.

### 6.5. Кластеры

Диаграмма кластеров строится k-means с **заданным** числом кластеров (метод сам k не выбирает). Практическая
ценность — не сама картинка, а просмотр связей конкретной страницы: семантически близкие соседи, входящие и
исходящие ссылки, «затесавшиеся» страницы.

## 7. API-обогащение краула

| Источник | Что даёт | Ограничение | Правило |
|---|---|---|---|
| GSC Search Analytics | клики, показы, позиция на URL; сироты (URL из GSC без внутренних ссылок) | окно ≥ 30 дней; склейка слэша — осознанно | фильтры «Non-Indexable с данными поиска», «URL not on Google», «Indexable URL not indexed» |
| GSC URL Inspection | индексация, выбранный Google canonical, rich results, дата обхода | 2 000 URL в сутки на одно подключение | пропускать неиндексируемые; квота растёт при подключении нескольких ресурсов (домен, префикс, папки) |
| PageSpeed Insights | CWV и лабораторные метрики | самый медленный источник: один запрос на URL | не отправлять «всё красное» разработчикам: формулировать задачи по шаблонам |
| Ahrefs / Majestic / Moz | ссылочные метрики URL | платный доступ | для выбора доноров перелинковки и приоритетов |
| LLM-провайдеры | колонки-обогащения | лимиты скорости ключа | запросы догоняют краул после его окончания |
